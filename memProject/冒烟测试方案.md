## 四、极端情况清单

| # | 场景 | 预期 |

| E1 | 空 `user_id` / 纯空格 | 422 |

## 五、执行方式与通过标准

**执行方式**：建议写成可重复的 Python 脚本（`httpx` + `asyncio`），按组串行跑、输出 PASS/FAIL 表。手工 curl 可做补充。

**通过标准**：
1. 所有正向用例 `code=0`（或对应 201/202）。
2. 所有负向用例返回预期错误码（401/404/422/409）。
3. 第三节「潜在问题」逐条给出结论：**修** 或 **记录为预期**。
4. 第四节「极端情况」全部不崩溃、行为符合预期。

**测试后清理**：`delete-all` 清理 `smoke_` 前缀数据。

## 六、指导者检查（补充）

> 标记为「指导者」外部检查。本轮修改（4.7 改 50 条、P1/P2/P3 修复）都很好，补充三个未解决点的提醒。

### 本轮修改的肯定

1. **4.7 改 50 条更充分**：50 条 = 前 4 批读满 20（连续满批续跑）+ 第 5 批读 10 不满批（等 timer 收尾），批次逻辑准确，能真正验证"海量导入不卡 timer"。
2. **P1/P2/P3 修复彻底**：尤其 P3 的"pipeline 用鉴权 agent_id"——不只是挡住无 key，而是"用鉴权身份归属记忆"，把身份和归属绑定，防止伪造 user_id。

### 三个未解决点（需在冒烟测试前/中确认）

**① P4（admin 端点未用 require_admin）——确认数据范围，决定是否必修**：

P4 未标注"已修复"。是否修取决于 **admin 端点暴露的是全量还是当前 agent 数据**：

- 若 `/admin/memories`、`/admin/logs` 暴露**全部用户数据** → 普通 agent 能看别人记忆 = 越权，应和 P2/P3 一样补 `require_admin`。
- 若只暴露**当前 agent 自己的数据** → 内网够用，可记录为预期。

**建议**：冒烟测试时确认 admin 端点的数据范围，若全量则 P4 升级为"必修"。

**② P7（async_write 走 Kafka）——明确死代码还是还在用**：

P7 标注"确认 async_write 实际行为（投 MQ 还是降级）"。需明确 async_write 现在状态：

- 已废弃但代码没删 → 死代码，应清理，冒烟测试确认"调 async_write 会怎样"。
- 还在用但无人调 → 决定去留，别让它悬着。

**③ P5/P6（字段重复）——确认"后定义覆盖前定义"的后果**：

P5（status、max_content_length 各定义两次）、P6（elapsed_ms 重复 key）。Python/Pydantic 里重复字段通常"后定义覆盖前定义"，功能可能正常，但可能导致"传参不生效"或"响应结构不稳定"。

**建议**：冒烟测试确认后，若"功能正常"则清理重复（低优先级卫生），若"传参不生效"则修。

### 总结

本轮修改（4.7 改 50 条、P1/P2/P3 修复）很好。三个未解决点中，**P4 最值得确认**——若 admin 端点暴露全量数据，它是和 P2/P3 同级的越权漏洞（只是"读"而非"改"）；P7/P5/P6 是"死代码/代码卫生"，优先级低但别悬着。
