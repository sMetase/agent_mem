# 多智能体记忆系统改造方案

> 本文档记录「从当前系统改造为多智能体记忆系统」的已确认结论与待办功能清单，作为后续逐个讨论细节的依据。
>
> 参考材料：
> 1. 自研《面向大模型智能体的记忆系统功能设计文档》
> 2. TencentDB Agent Memory 架构文档（`ARCHITECTURE_CN.md`）
> 3. 当前代码（`memProject/`）

---

## 一、结论记录

### 1. 记忆不跨场景（设计文档已明确）

- 设计文档明确：场景是**硬隔离**维度，不同场景记忆「严格切分、绝对不发生混用」。
- 支持的「跨」的范围：**跨会话 ✅、跨任务 ✅、跨场景 ❌**。
- 结论：不引入「跨场景共享」，场景隔离是对的，保留现状。

### 2. 需要透明代理（已确认）

- 痛点：当前外部 agent 需逐个调用 `/write`、`/search`、`/context`，成百上千 agent 逐个集成不可行。
- 结论：新建**透明代理（Proxy）**，agent 只改 base URL，记忆自动「召回注入 + 异步写回」，零代码接入。

### 3. 采用 L0–L3 分层记忆组织（已确认，用户偏好）

- 采用 TencentDB 四层记忆思想：
  - **L0 原始对话**：忠实记录，不做理解。
  - **L1 原子记忆**：抽取 + 去重（事实/偏好/任务/过程/反馈）。
  - **L2 场景**：把 L1 按场景/项目聚合成知识块。
  - **L3 画像**：长期稳定的用户/团队画像。
- **纵向**：L0→L1→L2→L3 层层浓缩（点→线→面），异步 pipeline + 游标驱动。
- **横向**：每层内部的组织（L1 多类记忆、L2 多场景块、L3 画像多维度）。

### 4. 记忆生命周期已实现（无需重做）

- 抽取、去重融合、多信号检索、长对话压缩、上下文返回——当前代码已实现，非瓶颈。

## 二、需要实现的功能清单（3 个工作流）

### 工作流 1：记忆核心 —— 补 L2 + 纵向异步蒸馏

| 层 | 现状 | 要做 |
|---|---|---|
| L0 原始对话 | ✅ `T_INTERACTION_RECORD` | 不动 |
| L1 原子记忆 | ✅ `T_MEMORY` + `memory_pipeline.py` + `memory_dedup.py` | 不动 |
| **L2 场景** | ❌ 完全缺 | **新建**：场景块存储 + 聚合逻辑 + 导航 |
| L3 画像 | ⚠️ `/profile` 接口独立，直接查 L1 | 改为**消费 L2**，纳入蒸馏链 |

- 核心改动：把「同步抽取」改为「**异步分层蒸馏 pipeline**」（写入只落 L0，后台 worker 按游标逐层 L0→L1→L2→L3）。

#### 块 A：L0→L1 异步化（已定）

把「落 L0」和「抽 L1」解耦：write 只落 L0 立即返回，后台异步抽 L1。

| 决策 | 结论 |
|---|---|
| worker 触发 | 单机 20-30 并发协程 + over-fetch backlog（读 20 处理 10，满页立即续跑） |
| 游标 | 落 DB（`memory_cursor` 表：cursor_key + last_processed_id），不用进程内 dict |
| 抽取分组 | 按 `(user, agent, session)` 分组，同 session 新消息拼接成 text，复用现有 `memory_pipeline` |
| 不丢不重 | 游标只推处理过的；**失败不推进游标**（下轮重抽同一批）；去重失败 storeAll 降级 |
| 载体 | 单机（20-30 并发），无需分布式 → **数据量庞大场景升级，见下「块 A 升级：Kafka」** |

#### 块 A 升级：Kafka 消息队列（规模升级，已定）

> 背景：原「块 A 载体」定为单机 20-30 并发 + DB 游标轮询。现数据量庞大（**日均数百万条**），落 L0 的瞬时峰值成为瓶颈，升级为 **Kafka 削落 L0 峰值**（**单机消费，不做分布式**）。
>
> 现状：项目已有 Kafka 雏形（`mq_producer.py` / `mq_consumer.py` + `config.py` 三 topic `memory.write`/`memory.result`/`memory.dlq`），但 `mq_consumer._dispatch_and_store` 是旧同步模式，需改造对齐。
>
> **最终收敛决策**：Kafka **只削「落 L0」瞬时峰值**（consumer 只落 L0 + 批量 insert）；**抽取不走 Kafka**（走游标轮询，靠并发 + 延迟消化）。write 只投 Kafka，Kafka 挂时降级同步落 L0。

**目标架构**

```
POST /memory/write ─→ 投递 Kafka (memory.write，消息带全量 L0 数据)
                          │  Kafka 不可用 → 降级同步落 L0（pending_extract）
                          ▼
        Kafka Consumer（单机，同 group）——只落 L0（批量 insert，削峰）
                          │
                          ▼
        t_interaction_record（pending_extract，天然背压队列）
                          │
                          ▼
        L1 worker（游标轮询）→ 抽取 → 落 L1 ─→ L2 ─→ L3（级联不变）
```

**详细设计**

| 项 | 方案 |
|---|---|
| Topic | 沿用已有 3 个：`memory.write`（写入消息）/ `memory.result`（结果回传，暂不用）/ `memory.dlq`（死信） |
| 消息格式 | **带全量 L0 数据**：`{request_id, user_id, agent_id, scene_id, session_id, task_id, interaction_type, messages[], session_summary, task_goal/task_progress/task_result, timestamp}`（即 MemoryWriteRequest 全量 + request_id） |
| 分区策略 | `key = user_id`（同 user 进同 partition，保证同 user 顺序）；**单机消费，无需分区并行扩展** |
| 生产者 | `/memory/write` 校验后**投递 Kafka**（带全量），投递成功返回 accepted；**投递失败 → 降级同步落 L0**（pending_extract） |
| 消费者 | 改造 `mq_consumer.py`：消费消息 → **只落 L0**（批量 insert），不触发抽取 |
| 幂等 | `request_id` 唯一约束 + `INSERT ... ON CONFLICT DO NOTHING`（DB 层保证，覆盖主/降级两条路径） |
| 重试/死信 | 失败指数退避重试 3 次（`max_retries=3`）→ 投 DLQ；失败不提交 offset（保证不丢） |
| 降级 | Kafka 不可用 → write 降级同步落 L0；L1 worker 低频轮询兜底（消费 pending_extract） |

**职责边界（关键）**：
- **Kafka**：只削「落 L0」瞬时峰值（150-300 insert/秒），consumer 批量 insert 削峰。
- **L1 抽取**：走 DB 游标轮询（`pending_extract` 积压天然背压），**不走 Kafka**——抽取是「持续吞吐」（30w 批/天 ≈ 16.7h/天），走 Kafka 会积压。

**实施步骤（分阶段）**

1. 抽统一 `persist_l0(payload)`：主路径（consumer）和降级路径（write）共用，`request_id` 唯一约束保证幂等
2. 改造 `mq_consumer.py`：消费消息 → 只落 L0（批量 insert，去掉旧「落 L0 + 同步抽取」）
3. `/memory/write` 改为投递 Kafka（带全量），投递失败降级同步落 L0
4. L1 worker 保持游标轮询抽取（已有，无需改，必要时提高并发）
5. 压测调优（批量大小 / 消费并发 / 消息大小）

**⚠️ 已标记问题（暂不处理）**：抽取吞吐 + LLM 成本。日均数百万条下，抽取吞吐（30w 批/天）+ LLM 成本（数亿 token/天）是比 Kafka 更本质的挑战——需大幅提高抽取并发（20-30 → 100+）或接受抽取滞后，且 LLM 成本需重新评估。Kafka 只解决「落 L0 峰值」，解决不了「抽取吞吐 + 成本」。**单独开讨论，本次不做处理。**

> **指导者评价**（Kafka 升级）：
>
> 决策合理——Kafka 削峰 + DB 降级兜底是标准做法。幂等（request_id）、分区（key=user_id）、降级、分阶段实施都考虑到了。三个需重点关注：
>
> **① 降级路径引入"两条写入路径"，是最复杂的部分**：主路径（write→Kafka→consumer 落 L0）和降级路径（write→直接落 L0→低频轮询）都落 L0，两个隐患——落库逻辑要统一、幂等要覆盖两条路径（Kafka 恢复后不能重复落降级期的数据）。**建议**：抽统一 `persist_l0(payload)`，两条路径都调它，幂等键统一用 request_id 唯一约束。
>
> **② request_id 幂等的具体实现要明确**：request_id 从哪来（write 侧 UUID？）、去重怎么查（DB 唯一约束还是应用层查重）。**建议**：t_interaction_record 加 request_id 唯一索引（或单独幂等表），`INSERT ... ON CONFLICT DO NOTHING`——用 DB 唯一约束保证幂等，而非应用层查重（并发下有竞态）。
>
> **③ "单机消费"的吞吐上限是削峰能否成立的前提**：Kafka 削峰价值是"缓冲峰值"，前提是消费速度 ≥ 生产速度，否则 Kafka 积压到磁盘满。单机 consumer 的"落 L0 + 触发 L1 抽取"（L1 是 LLM 调用，几秒）能否跟上峰值生产速度，必须压测验证。若跟不上，要么提高消费并发，要么"消息只投 L0 数据、L1 抽取仍走 DB 游标轮询"（解耦落 L0 和抽取）。

> **求解者疑问（待指导者解答，不假设）**：
>
> 指导者「consumer 只落 L0 + 抽取走游标轮询」的建议，引出一个更深层疑问——**Kafka 到底在削「谁」？**
>
> **疑问①（削峰对象存疑）**：若 consumer 只落 L0，Kafka 削的是「落 L0」（毫秒级 DB insert，通常非瓶颈）；而真正慢的「L1 抽取」（LLM 几秒）走回了游标轮询（DB 背压），根本不经过 Kafka。Kafka 削了个本来就快的东西，意义存疑。
>
> **疑问②（相比现状的增量）**：若 consumer 只落 L0，与当前架构「write 同步落 L0 + 游标轮询抽取」相比，Kafka 只是把「落 L0」从 write 同步挪到 consumer 异步，多了一层 Kafka 延迟/复杂度。多出的这层 Kafka 换来了什么？候选：(a) write 需不碰 DB 更快返回；(b) 写入高峰落 L0 扛不住需缓冲；(c) 想要消息队列形态、为扩展留余地。
>
> **疑问③（最根本）**：数据量庞大的瓶颈到底是「落 L0」（写入 QPS）还是「抽取」（LLM 吞吐）？
> - 若瓶颈在「落 L0」→ Kafka 削落 L0 有意义，指导者「consumer 只落 L0」方向成立。
> - 若瓶颈在「抽取」→ Kafka 应削抽取，但削抽取会积压（方案 X 问题）；且抽取背压当前 DB 的 `pending_extract` + 游标轮询已在承担，Kafka 非必需。
>
> **待明确（求解者不假设）**：
> 1. 数据量庞大的具体瓶颈：写入侧（落 L0 QPS）还是抽取侧（LLM 吞吐）？量级（写入 QPS / 日均消息数）？
> 2. 引入 Kafka 的真实动机：落 L0 扛不住要削峰？还是消息队列解耦 + 未来扩展？
>
> 回答这两个后，才能判断指导者建议是否采纳、Kafka 该削谁、甚至 Kafka 是否必要。

> **指导者解答（澄清：后期写入数据会到几百万）**：
>
> 求解者三个疑问成立且尖锐。但用户澄清"后期写入数据到几百万"后，之前的"Kafka 过度设计"结论要修正——**几百万/天下，落 L0 和抽取都成了瓶颈，但性质不同**。
>
> **瓶颈重算（日均 300w 条）**：
>
> | 侧 | 量级 | 是否瓶颈 |
> |----|------|---------|
> | 落 L0（写入 QPS） | 峰值 ~150-300 insert/秒 | ⚠️ 是（瞬时峰值瓶颈，PG 有压力） |
> | 抽取（LLM 吞吐） | 30w 批/天，20-30 并发 ≈ 16.7h/天 | ⚠️ 是（持续吞吐瓶颈，接近全天满负荷） |
>
> **回答疑问③**：两个都是瓶颈，但性质不同——落 L0 是「瞬时峰值」（适合 Kafka 削峰），抽取是「持续吞吐」（不适合 Kafka，会积压）。
>
> **回答疑问①**：几百万/天下，「落 L0」确实是瓶颈（瞬时峰值），所以 Kafka 削落 L0 **有意义**。之前质疑"削的是本来就快的东西"是基于 10w/天（落 L0 非瓶颈），几百万/天下结论反转。
>
> **回答疑问②**：增量变为「削落 L0 瞬时峰值 + consumer 批量 insert」——write 投 Kafka 快速返回（不碰 DB 峰值），consumer 批量落 L0 削峰。
>
> **修正后的结论**：Kafka 只削「落 L0」（consumer 只落 L0 + 批量 insert），**抽取不走 Kafka**（走游标轮询，靠并发 + 延迟消化）。这验证了求解者质疑的「consumer 只落 L0 + 抽取走游标轮询」设计，在几百万/天下是对的。
>
> **必须补充的提醒（更本质的挑战）**：几百万/天下的「抽取吞吐（30w 批/天）+ LLM 成本暴增」是比「Kafka 削谁」更本质的问题——抽取要大幅提高并发（20-30 → 可能 100+），或接受抽取延迟（滞后几小时），且 LLM 成本要重新评估（30w 批/天 × token ≈ 数亿 token/天，远超之前"4000w/天可接受"）。Kafka 只解决"落 L0 峰值"这一小块，解决不了"抽取吞吐 + 成本"。

#### 块 B：L2 场景层（决策 1：形态已定）

- **采用「折中版」**：PG 表 `T_SCENE_BLOCK`（content 存叙事全文）+ 单次 LLM 全文重写（保留深度整合，L3 有叙事可抽象）。
- **保留「完整版」待评估**：Agent + 文件沙箱 + .md 文件 + 索引/导航（文档第十六节）。后续评估「场景块数量/长度上来后，token 成本 vs 按需 read 灵活性」，再决定是否升级。
- **关键澄清**：文档「L2 场景」= 主题场景块（LLM 自动命名，如"日本旅行"），≠ 现有业务场景 `T_SCENE`（客服/物流，隔离用）。

#### 块 B 决策 2：聚合粒度已定

- **L2 场景块 + L3 画像 → 按 `(scene_id, user_id)` 归属（跨 agent）**。
- **智能体执行经验（工具轨迹、失败原因）→ 单独按 agent 存，不进场景/画像**。
- 场景块主题（scene_name，如"日本旅行"）由 LLM 在该 user 范围内自动命名；「归属」和「主题」是两个正交维度。
- 依据：设计文档「用户级记忆」（偏好、业务关注、项目背景）是 user 维度、跨 agent；「智能体状态记忆」（执行经验）是 agent 维度。

#### 块 B 决策 3：触发时机已定

- **级联触发 + 三级 timer + 增量消费（游标）**。
- 轻量版先简化为「级联 + 固定 delay（30 秒）」，验证链路 + 聚合质量后，升级加 `l2MinIntervalSeconds`（防频繁聚合）+ `l2MaxIntervalSeconds`（兜底）两参数。
- 消费范围：增量 L1 记忆（`updatedAfter` 游标之后的新记忆），不全量重算。

#### 块 C：L2→L3 画像联动（已定）

把当前独立的 `/profile` 画像接口改成「消费 L2 场景块」的 L3 画像层，纳入蒸馏链。

- **C1 触发节奏**：按「L1 新记忆条数」触发（`memories_since_last_persona >= N`），加 5 优先级（主动请求 / 冷启动 / 恢复 / 首次 / 攒够 N 条）。
- **C2 增量范围**：只读变化场景（`first` 模式全量 / `incremental` 模式只读 `updated > last_persona_time`），无变化跳过。
- 形态复用块 B 折中版（单次 LLM + PG 表存 persona）；聚合粒度复用 `(scene_id, user_id)`。

### 工作流 2：接入层 —— 新建透明代理（Proxy）

- 现状：无。
- 要做（四件事）：
  1. 接收 Agent 的 LLM 请求（OpenAI / Anthropic 协议，读 messages 里的用户输入）。
  2. **召回注入**：调 Core 拿 L1 相关记忆 + L2 导航 + L3 画像，塞进 prompt。
  3. **转发**上游 LLM（含流式）。
  4. **异步写回**：写 L0 → 触发蒸馏。

#### P0 透明代理流程详情

**完整流程**：

```
外部 Agent（Claude Code / 自研 agent）
  │ 改 base URL 指向 Proxy，照常发 LLM 请求
  ▼
Proxy（挂现有 FastAPI）
  ① 接收 LLM 请求（OpenAI /v1/chat/completions）→ 解析 messages、model
  ② 鉴权：URL 里的 spaceId → 查 spaces.yaml → user_id / api_key / scene_id / agent_id
  ③ 会话：sessionKey 从 header 提取，首轮调 /session 建会话（后续复用）
  ④ 召回：调 /memory/context → formatted_text（当前只 L1；L2 导航、L3 画像为后续注入器）
  ⑤ 注入：L1 记忆拼进 user prompt 前缀（动态；L2/L3 将来拼 system 尾部）
  ⑥ 转发：请求转给真 LLM（DeepSeek，透传 model，忽略 stream）
  ⑦ 异步写回：调 /memory/write（本轮用户消息 + 回复 → 只落 L0）
  ▼
真 LLM → 回复原路返回 → Agent → 用户
```

**接口调用**：

| 步骤 | 接口 | 归属 |
|---|---|---|
| ③ 建会话 | `POST /api/v1/session`（write 要求 session_id） | ✅ 现有 |
| ④ 召回 | `POST /api/v1/memory/context` | ✅ 现有 |
| ⑦ 写回 | `POST /api/v1/memory/write` | ✅ 现有 |
| Proxy 暴露 | `POST /proxy/{spaceId}/v1/chat/completions`（OpenAI 兼容） | 🆕 新建 |

> 结论：P0 不碰记忆核心，只用现有 3 个接口。

**两个新增机制（Proxy 自己，非记忆接口）**：

1. **spaceId 鉴权**：外部 agent 不带 `X-API-Key`，用 URL 的 `spaceId` 做身份，Proxy 配置存映射 `{spaceId → {user_id, api_key, scene_id, agent_id}}`。其中 `api_key` 是**记忆系统的 X-API-Key**（预注册智能体的 key，调 /memory/* 用），**不是上游 LLM 的 key**（上游 LLM 复用 DEEPSEEK 环境变量）。
2. **会话识别（sessionKey）**：sessionKey 由接入层（Agent 客户端）定义，Proxy 从 header 提取，映射到我们的 session_id。

#### sessionKey 会话识别设计（已定）

- **sessionKey（通道）**：接入层传入的会话 ID，从请求 header 提取。
  - 候选 header 名：`x-conversation-id` / `x-session-id` / `x-claude-code-session-id` / `x-deepseek-harness-session-id` / `x-chat-id` / `x-thread-id`。
  - 现成客户端（Claude Code 等）：被动兼容它们的 header 名。
  - 自研 agent：自己定义，主动传 `x-conversation-id` / `x-session-id`。
- **sessionId（实例）**：reset 触发变化；轻量版先简化为「= sessionKey」（无 reset 概念）。
- **fallback**：header 无会话 ID 时，用 spaceId 兜底（一个接入方一个通道）。
- **核心原则**：sessionKey 永远是接入层定义的，记忆系统/Proxy 只负责「提取 + 按它隔离」。

**具体例子**（用户说「帮我继续日本旅行规划」）：

```
① Agent → Proxy：POST /proxy/space_001/v1/chat/completions
   {"model":"deepseek-chat","messages":[{"role":"user","content":"帮我继续日本旅行的规划"}]}
② Proxy 取 spaceId=space_001 → user_id=user_001、api_key=mem_xxx
③ 调 /memory/context(query=帮我继续日本旅行的规划) → formatted_text
④ 把 formatted_text 拼进 system prompt
⑤ 转发给 DeepSeek
⑥ DeepSeek 回复原路返回；Proxy 后台异步调 /memory/write 写回
```

## 附录：指导者评价

> **说明**：以下为「指导者」基于 TencentDB Agent Memory 架构经验对本文档的剖析，标记为外部评价，非方案作者结论，供方案作者参考决策。

### 一、合理可采纳的（亮点）

1. **概念澄清：L2 场景块 ≠ 业务场景 T_SCENE** —— 全方案最关键的一个澄清。TencentDB 的"场景"（L2）是主题聚合（LLM 自动命名，如"日本旅行"），而现有系统的 `T_SCENE` 是业务隔离（客服/物流）。两者正交：一个管"记忆怎么组织"，一个管"记忆怎么隔离"。**必须保留，否则实现 L2 时会误以为要复用 T_SCENE。**

2. **聚合粒度区分：用户级记忆 vs 智能体状态记忆** —— 抓住了"记忆主体"的本质。"认知类"记忆（偏好/画像）主体是 user、跨 agent 共享；"执行类"记忆（过程/失败）主体是 agent、私有。这比 TencentDB 的"统一按 agent 聚合"更贴合"多 agent 服务同一 user"的业务。

3. **折中版 L2：PG 表 + 单次 LLM 全文重写** —— 避免 Agent + 文件沙箱 + .md 的复杂度，是正确的轻量版取舍。TencentDB 的 Agent 模式是为"按需 read 场景、省 token"，轻量版场景块少，单次重写更简单。"先简后繁"的节奏正确。

4. **sessionKey 识别：完整复用 header 提取机制** —— 6 个候选 header 名 + fallback，直接照搬 TencentDB 的 `resolveConversationId`，经过了多客户端实战验证，可直接采纳。

5. **P0 不碰记忆核心** —— Proxy 只用现有 3 个接口，渐进式正确：先打通"零代码接入"核心价值，再改内部结构。

### 二、需要进一步思考的（隐患）

1. **Q5 与块 A 的矛盾：over-fetch 到底做不做**（已澄清：项目确为海量导入）—— 块 A 说"over-fetch backlog（读 20 处理 10）"，Q5 说"简化成读 N 处理 N"，两处矛盾。**修正建议**：海量导入场景下，**统一为 over-fetch（读 20 处理 10）**。但更本质的是：海量导入需要"**满批立即续跑**"（处理完一批立即处理下一批），over-fetch 只是"检测积压、触发续跑"的实现之一（用"多读 10 条"换"少查一次剩余"）。也可选"读 N 处理 N + 处理完立即再查剩余"，两者都能快速消化，但**"满批立即续跑"这条红线不能丢**——否则海量导入每 10 条等一次 timer，几千条要几十分钟。

2. **游标"进程内 dict"的重启丢失** —— 重启后游标丢失 → 从 0 重抽（重复）或抽不到。**建议游标落 DB 一列**：`cursor_key = (user_id, agent_id, session_id)` → `last_processed_id`（自增 record id，Q1 已定），每次抽取**成功后**才更新，重启读回无缝继续。额外好处：天然支持未来升级多 worker（游标在 DB 里可共享）。配合"失败不推进游标"，不丢不重。

3. **"JSON 失败下轮重抽"的游标语义** —— 未明确"失败时游标推进不推进"。这是"不丢"的核心：**失败时不推进游标，下轮自然重抽同一批**；失败也推进则这批消息永久丢失。

4. **fallback 用 spaceId 兜底 session 的并发隐患** —— "一个接入方一个通道"，若一个 spaceId 对应多个并发会话（同一 Claude Code 多窗口、多用户共用 spaceId），会话会串。轻量版可接受，但要知晓限制。

5. **优先级 P0（Proxy）先于 P1（L0-L3）的返工** —— Proxy 依赖核心的召回/写回。先做 Proxy 调用的是旧 `/memory/context`（只有 L1），等 P1 做完 L2/L3 后召回注入要改（"只 L1"→"L1+L2 导航+L3 画像"）。**建议先核心后接入**（块 A→块 B→块 C→Proxy），Proxy 一开始就能用完整召回；若想尽早 demo"零代码接入"，先 Proxy 也可，接受一次召回拼装逻辑的返工。

6. **工作流 1 切入点：先异步骨架，再做 L2** —— L2 的增量消费依赖 L1 的异步产出（`updatedAfter` 游标），若 L1 还是同步抽取，L2 没有稳定的"增量 L1 记忆"来源。依赖链 `块 A（L1 异步）→ 块 B（L2 消费 L1 增量）→ 块 C（L3 消费 L2 变化）` 顺序不能乱。

7. **治理层"隔离 vs 授权"的边界** —— 方案 A 用"隔离"代替"授权"（scene/user 维度物理隔离，默认不共享），符合"记忆不跨场景"结论。但要清醒：**隔离只能做到"不混"，做不到"主动共享"**；未来要"跨 user 共享"（团队共享 SOP）就需要授权表。已预留"方案 B 下一迭代"，正确。

8. **Q12 开鉴权 vs 方案 A 不开授权，两者要分清** —— 鉴权（Q12）是"识别你是谁"（X-API-Key → agent_id + scene_id），授权（方案 A）是"控制你能读谁"（scene 隔离代替）。两者是"身份识别"和"访问控制"两个层面，都要有（鉴权开、授权用隔离代替），不冲突。

| 类别 | 条目 | 结论 |
|------|------|------|
| ✅ 合理 | L2 场景块 ≠ T_SCENE 的澄清 | 必须保留 |
| ✅ 合理 | 用户级记忆 vs 状态记忆的粒度区分 | 比 TencentDB 更细，贴合业务 |
| ✅ 合理 | 折中版 L2（PG 表 + 单次重写） | 正确的轻量取舍 |
| ✅ 合理 | sessionKey header 提取 | 直接采纳 |
| ✅ 合理 | P0 不碰核心 | 渐进式正确 |
| ⚠️ 需思考 | Q5 与块 A 的 over-fetch 矛盾 | 海量导入场景，统一为 over-fetch（读 20 处理 10）+ 满批立即续跑 |
| ⚠️ 需思考 | 游标进程内 dict 重启丢失 | 落 DB 一列 `(user,agent,session) → last_processed_id` |
| ⚠️ 需思考 | JSON 失败游标推进语义 | 明确"失败不推进游标" |
| ⚠️ 需思考 | fallback spaceId 兜底的并发会话隐患 | 知晓限制 |
| ⚠️ 需思考 | 优先级 Proxy 先的返工 | 建议先核心后接入 |

**整体评价**：核心判断（分层、代理、粒度区分、折中取舍）都是对的，可直接推进。最需立刻解决的两个内部矛盾/隐患：① Q5 与块 A 的 over-fetch 不一致（已澄清项目为海量导入，统一为 over-fetch + 满批立即续跑）；② "JSON 失败重抽"的游标推进语义没明确（失败不推进游标）——这两个直接关系到"不丢不重"能否实现。另补充：游标建议落 DB 一列，避免进程内 dict 重启丢失。

### 补充论证：游标「落 DB 一列」vs「进程内 dict」

**建议：落 DB 一列**。理由不是"进程内 dict 不能用"，而是"落 DB 成本几乎为零，进程内 dict 在海量导入下风险代价高"。

**成本对比**：

| | 进程内 dict | 落 DB 一列 |
|---|---|---|
| 成本 | 零 | 每批一次 UPDATE（可忽略） |
| 重启后 | 全量重抽（海量导入=几千次 LLM 浪费） | 无缝继续 |
| 未来多 worker | 不支持 | 天然支持 |

**核心论证**：落 DB 的成本是"每批抽取成功后一次 `UPDATE`"，相比"一次 LLM 调用（几秒）"完全可忽略；而进程内 dict 重启丢游标 → 全量重抽 → 海量导入场景下浪费几千次 LLM 调用，代价高几个数量级。**用可忽略的成本，规避高代价的风险。**

**待确认前提**：服务重启后进程内 dict 游标丢失，实际怎么处理？（A 重置为 0 全量重抽 / B 有扫描恢复机制 / C 未想清楚）——无论哪种，落 DB 建议不变（A 价值最大、B 更简单、C 直接解决）。

**进程内 dict 仅当同时满足才可接受**：① 服务基本不重启；② 数据量小（全量重抽不贵）；③ 确定单机永不扩展。海量导入场景不满足 ②，故不适用。

**具体设计**：

```sql
CREATE TABLE memory_cursor (
  cursor_key VARCHAR PRIMARY KEY,      -- `${user_id}:${agent_id}:${session_id}`
  last_processed_id BIGINT NOT NULL,   -- 最后处理的 L0 record id（自增 id）
  updated_at TIMESTAMP DEFAULT now()
);
```

每次抽取**成功后** `UPDATE last_processed_id = 本批最后一条 record id`；重启读回游标，从 `record_id > last_processed_id` 继续；失败不推进（对应隐患 3，保证不丢）。

### 优先级建议：P0（Proxy）先，还是 P1（核心）先

**默认倾向：B（先 Proxy）**，但前提是 Proxy 的召回注入做成「可插拔注入器」。

**决策取决于两个前提**（需方案作者确认）：

1. 「零代码接入」方案有多确定？（已想清楚 vs 需验证）
2. demo 时间压力多大？（急 vs 不急）

**为什么倾向 B（先 Proxy）**：

- 「零代码接入」是方案灵魂（痛点就是"成百上千 agent 逐个集成不可行"），最有风险、最该早验证——改 base URL 是否无感、header 提取是否够覆盖客户端、异步写回时序是否跑通，这些"接入层"的坑**不依赖 L0-L3**，先做能早暴露。
- **返工可通过「可插拔注入器」降到很低**：硬编码"拼 formatted_text"后续加 L2/L3 要改逻辑；可插拔（`injectors = [L1MemoryInjector()]` → 后续 `+ L2NavInjector() + L3PersonaInjector()`）是"加注入器"而非"改逻辑"。
- 诚实说明：返工非零（核心召回接口返回结构变了，Proxy 仍要适配），但量级从"重写拼装"降到"加模块 + 适配"。

**什么情况选 A（先核心）**：「零代码接入」已确定可行 + 不急 demo + 追求一次性做对——此时"早验证"的收益小，"避免返工"的价值大。

**折中（拿不准时）**：做「最小 Proxy」（接收 → 召回 → 注入 → 转发 → 写回的最小闭环），召回注入一开始就用可插拔注入器——尽早验证零代码接入，后续加 L2/L3 是加注入器，返工最小。

| 前提 | 建议 |
|------|------|
| 零代码接入不确定 / 急着 demo | B 先 Proxy（注入可插拔） |
| 零代码接入已确定 / 不急 demo | A 先核心 |
| 拿不准 | 最小 Proxy + 可插拔注入器 |

**待确认**：① 零代码接入的确定性；② demo 时间压力。确认后收敛为明确答案。

### 规模修正（澄清：2000 智能体 + 日均 10w 消息）

**澄清前提**：10w 是 L0 消息数；2000 个 Agent 可能同时活跃；LLM 4000w token/天可接受；检索性能未测验。

**关键区分：接入层并发 ≠ 核心层吞吐**：

| 层 | 挑战 | 量级 |
|----|------|------|
| 接入层（Proxy） | 2000 agent 同时活跃 → 2000 并发连接 | 连接数 |
| 核心层（worker） | 日均 10w → 峰值 ~5 条/秒（均匀）或突发更高 | 吞吐 |

2000 同时活跃影响的是"接入层扛 2000 并发连接"，不是"核心层处理 2000 条/秒"。

**重新考量后的建议**：

1. **接入层**：FastAPI 异步能扛 2000 并发，但**前提是全程异步**——LLM 转发、召回调用、写回都用异步客户端（httpx.AsyncClient），否则同步阻塞会爆。
2. **核心层**：单机 **20-30 并发协程**（留余量应对突发，而非均匀峰值的 5-10 个）+ **over-fetch 满批立即续跑**（突发积压时快速消化）。不需要分布式。
3. **LLM 成本**：可接受，**不用过度优化抽取频率/批量**，按 10 条/批正常做。
4. **检索性能（最大未知风险）**：日均 10w 累积 300w/月，现状检索未测——**建议尽早做一个 300w 量级的检索压测**，直接决定"召回注入"能否用（召回慢则每轮都等）。

**收敛**：

| 之前建议 | 修正后 |
|---------|--------|
| worker 单协程 asyncio | 单机 20-30 并发协程 + 满批立即续跑 |
| Proxy 挂 FastAPI | 仍对，但确认全程异步 |
| 游标落 DB | 不变（1w 次写/天，非瓶颈） |
| over-fetch | 不变，且更重要（应对突发） |
| 检索性能 | 新增风险点，尽早压测 |

### 开发阶段建议（进入开发前需补充）

方案本身可开发，但 13 个任务全是"实现"，缺四类配套：

**① 每个块完成后加「验证」环节**：13 个任务全是实现，无验证/质量检查。开发阶段最易出的问题不是"写不出"，而是"写出来质量不对、做到底才发现"。

| 块 | 完成后验证什么 |
|----|--------------|
| 块 A（L1 异步化） | write 落 L0 → 异步抽 L1 链路跑通，抽取质量与同步时一致 |
| 块 B（L2 场景层） | L1 增量 → L2 聚合，场景命名准不准、叙事质量好不好（单次 LLM 重写质量是最大不确定） |
| 块 C（L3 画像） | L2 变化 → L3 更新，画像是否凝练、是否有幻觉 |
| 全链路 | L0→L1→L2→L3 端到端跑通 |

**② 检索压测不能"本阶段暂不做"，要提前到 Proxy 接入前**：检索是最大风险，其影响在 Proxy 接入时才暴露（每轮 /context 召回慢 → 零代码接入体验差）。建议 P1 完成后、P0 接入前，灌 300w 条 L1 测检索延迟；扛不住则 P1 阶段就优化，而非等 Proxy 接入才发现。

**③ 明确「数据迁移/兼容」**（块 A/C 改动影响现状数据）：
- 块 A 同步改异步：现有已同步抽好的 L1 记忆**保留还是重抽**？有无调用方依赖"write 同步返回 L1"？
- 块 C /profile 改消费 L2：现有 /profile 画像数据**废弃还是迁移**？

**④ 补一个「监控/可观测」任务**：日均 10w 无监控无法运维。至少加：worker 积压数（游标落后多少）、抽取失败率（LLM 失败/JSON 失败各多少）、每层产出速率。没有它们，出问题只能靠猜。

**⑤ 明确「级联触发」的信号传递**（块 A 完成怎么通知块 B）：建议轻量版用"块 B 定时扫描 L1 增量（updatedAfter 游标）+ delay 30s 兜底"，不需要块 A 显式通知——块 A/B 解耦，各自独立跑。

**最该先补的是「验证」和「检索压测提前」**——一个保证"做对了"，一个规避"最大风险晚发现"。

### L0 落库后的响应（块 A 异步化的具体细节）

**L0 落库后的响应只有"落库确认"，不含 L1 抽取结果**——因为 L1 是异步的，落 L0 时还没抽。

TencentDB 的 `performAutoCapture`（写 L0）返回 `{ schedulerNotified, l0RecordedCount, l0VectorsWritten, filteredMessages }`，**不含 L1**——capture 只做"落 L0 + 通知调度器"，L1 由后台调度器异步抽。

**建议 write 响应结构**（改后异步）：

```json
{
  "accepted": true,          // 落库成功
  "session_id": "sess-xxx",
  "l0_count": 3,             // 落了几条 L0
  "record_ids": [...]        // 可选，落库 record id 供追溯
}
```

**不含 L1**——这是"异步化"的语义：write 只确认"记下来了"，L1 的结果调用方不该等（否则又变回同步，write 延迟 = 落 L0 + LLM 抽取几秒）。

**需排查**：现有代码是否有调用方依赖"write 同步返回 L1"（写完立即读 L1）——这些要改成"写完后稍后再查 L1"，否则异步化后读不到。
