## 指导者检查（2026-08-18）

> 标记为「指导者」外部检查，非开发结论。整体质量高：现状确认到位、前提区分清晰、验证结果明确。

### 做得好的

3. **验证结果到位**：验证"write 立即返回 + T_MEMORY 无新增"，确认"不再同步抽 L1"生效。
4. **游标 key 与方案一致**：`(user_id, agent_id, session_id)` 与方案块 A 一致。

### 需要澄清/注意的（4 个点）

**① 「游标」和「status」的关系要理清**（日志表述含糊）：

"按游标扫 pending_extract"把两个机制混在一起。正确关系：游标管进度（worker 扫 `id > cursor`），status 管单条状态（抽完改 `processed`）。两者互补，不是重复。块 A worker 实现时要明确"以游标为准，status 为辅"。

**② scene_id / task_id 不在游标 key 里（最需立刻澄清）**：

L0 表有 `scene_id`/`task_id`，但游标 key 是 `(user, agent, session)`。方案结论 1 说"scene 是硬隔离"，这里要澄清：

- 若 session↔scene 是 1:1 → 游标不含 scene 没问题（session 隐含 scene）。
- 若 session 可能跨 scene → 按 `(user, agent, session)` 抽取会把不同 scene 消息混抽，违反"scene 硬隔离"。

**建议**：确认"session ↔ scene"关系（1:1 还是 1:N）；若 1:N，游标 key 要考虑加 scene 维度，或 L1 抽取按 scene 过滤。

**③ 现有 Kafka MQ 的去留（要确认完整用途）**：

现有系统已有 async_write + Kafka MQ，方案 Q2 决策用 asyncio 废弃 Kafka。但 Kafka MQ 是否只用于记忆抽取？若还承担别的功能，废弃会误伤。块 A worker 实现前确认 async_write/mq_consumer 的完整用途。

**④ 「异步抽取」完整链路未验证（要补）**：

日志验证了"write 不再同步抽"（改对了），但"异步抽 L1"的完整链路（worker 扫 L0 → 抽 L1 → 推进游标）要等 worker 做完后补端到端验证。

### 总结

块 A-1（建表 + write 异步化）做得对、验证对。最需立刻澄清的是**② scene_id 与游标 key 的关系**——直接关系到"scene 硬隔离"能否在抽取层落地。

### 澄清后更新（用户确认 agent↔scene 1:1）

**① 隐患 2 划掉**：确认 agent↔scene 是 1:1，游标 key 不含 scene_id 是对的——agent 隐含 scene，按 `(user, agent, session)` 分组天然按 scene 隔离。

**② edge case 兜底方式修正**（用户日志写的是"跳过/告警"，建议改为"从 agent 推导"）：

- `L0.scene_id` 是 L1→L2 归属链路的源头：`L0.scene_id →（L1 继承）→ L1.scene_id →（L2 归属）→ L2.scene_id`。
- 若 L0.scene_id 是 None，链路断——L1 拿不到 scene、L2 无法归属。
- "跳过/告警"会导致丢数据（跳过）或链路断（告警但缺 scene）。
- **正确兜底**：既然 agent 1:1 绑 scene，session 的 scene 应始终能从 agent 推导：

```python
scene_id = l0.scene_id or agent.scene_id  # 从 agent 推导兜底
```

- **更优**：session 创建时就强制填充 scene_id（从 agent 推导），问题在源头解决，worker 无需兜底。

**核心提醒**：`L0.scene_id` 不能容忍 None——否则 L1 抽取、L2 归属全断。"从 agent 推导"是零成本的正确兜底，"跳过/告警"会导致丢数据或链路断。

## 2026-08-18 · P1-A-2 + P1-A-3：异步 worker + L1 抽取拼接 + 游标推进

### 已完成

新建 `app/services/l1_worker.py`，实现 L1 异步抽取 worker：

- **主循环** `l1_worker_loop`：定时轮询（POLL_INTERVAL_SECONDS=5），over-fetch 满批续跑。
- **参数**：`L1_BATCH_QUERY=20`（over-fetch 读 20）、`L1_BATCH_PROCESS=10`（处理 10）、`WORKER_CONCURRENCY=25`（asyncio.Semaphore 限并发）。
- **发现 pending**：查 `status='pending_extract'` 的 L0，`GROUP BY (user, agent, session)`。
- **读增量**：按游标 `id > last_processed_id` 读（游标管进度，主驱动），`status='pending_extract'` 辅助。
- **拼 text**（Q3）：`[record_id] [role]: content`，`source_record_ids` 带 record_id 追溯。
- **scene_id 兜底**：`l0.scene_id or agent.scene_id`（从 agent 推导，L0.scene_id 不能 None）。
- **游标推进**：成功后推进 `last_processed_id` + 标记 `processed=True, status='processed'`；失败不推进（下轮重抽）。

`app/main.py`：lifespan 里启动 worker 后台任务（`asyncio.create_task`），关闭时 `stop_event` 停止。

### 关键实现点

- `pipeline.run` 用 `db.flush()` 不 commit，worker 自己 `await db.commit()`；失败 `db.rollback()`。
- 每个 group 独立 db session（`async_session_factory`），避免并发协程共享 session。
- `_process_group` 返回「是否满批」，满批 → 主循环 `continue` 立即续跑（不等 timer）。

### 验证结果（端到端）

- write 落 L0（2 条 pending_extract）→ worker 扫到 → 抽 L1（1 条 task_state）→ 游标推进到 25596 → L0 标记 processed。
- 确认「write 立即返回 + 后台异步抽 L1 + 游标落 DB + 失败不推进」整条链路跑通。

### 发现的迁移问题（需注意，非代码 bug）

切换同步→异步后，历史测试数据里「已同步抽过但 status 仍是 pending_extract」的 L0 会被 worker **重新抽取**（游标从 0 开始）。部署到生产时需：上线前把存量 L0 标记 processed 或初始化游标跳过，避免重复抽取。测试环境影响不大（dedup 会兜底合并/跳过）。

### 关键设定（后续块 B/C 会用到）

- 游标表 `t_memory_cursor`：cursor_key=`user:agent:session`，last_processed_id=最后处理的 L0 id。
- L1 记忆通过 `pipeline.run` 写入时已带 `scene_id`（从 L0 取 + agent 兜底），这是 L2 归属的源头。
- worker 是单机 asyncio（20-30 并发），无需分布式；后续块 B（L2）会「定时扫描 L1 增量」级联触发。

## 指导者检查（P1-A-2/A-3）

> 标记为「指导者」外部检查。整体做得很好——采纳了之前所有建议（scene_id 从 agent 推导、独立 db session、并发控制、满批续跑），端到端验证跑通。

### 做得好的

1. **scene_id 兜底采纳建议**：`l0.scene_id or agent.scene_id`，正是"从 agent 推导"。
2. **并发 + over-fetch 符合设计**：25 并发（Semaphore）+ 读 20 处理 10 + 满批续跑。
3. **独立 db session + 手动 commit/rollback**：正确的并发实践。
4. **主动发现迁移问题**：识别"历史 pending_extract 会被重抽"。
5. **端到端验证完整**：write → worker → 抽 L1 → 游标推进 → 标记 processed，全链路跑通。

### 需要澄清/注意的（2 个点）

**① 失败时 status 的行为没明确（最关键）**：

日志只写"失败不推进游标"，但**失败时 status 改成什么没明确**。这是"不丢"的关键：

- worker 有两个机制定位"要处理什么"：`status='pending_extract'`（发现 pending）+ `id > cursor`（读增量）。
- 若失败时 status 被改成别的（如 `'failed'`），则"发现 pending"找不到该组，但"读增量"（游标没推进）还能读到——两机制矛盾，可能漏抽。

**正确做法**：失败时 status **保持 `'pending_extract'` 不改**，只"游标不推进"——下轮两机制都能再次找到，自然重抽。

**② 游标推进 + status 标记的原子性**：

游标推进（`UPDATE last_processed_id`）和 status 标记（`UPDATE status='processed'`）**必须在同一个事务（同一 commit）**：

- 游标推进但 status 没改 → 下轮"发现 pending"找到组，但"读增量"读不到（空转）。
- status 改了但游标没推进 → 下轮"读增量"还能读到，但"发现 pending"找不到（漏）。

从"pipeline.run flush + worker commit"看大概率是原子的，但需明确。

### 总结

P1-A-2/A-3 做得对、验证对。唯一需澄清的是**失败时 status 的行为**（应保持 `'pending_extract'` 不改），以及**游标推进 + status 标记的原子性**——两点都关系到"不丢不重"。

### 澄清回应（核对代码，两点均正确）

**① 失败时 status 的行为**：代码已正确处理——失败时 `await db.rollback()`，status **保持 `pending_extract` 不改**，游标不推进。下轮两个机制（`status='pending_extract'` 发现 pending + `id > cursor` 读增量）都能再次找到该组，自然重抽，不丢不重。已补注释明确。

**② 原子性**：游标推进（cursor 对象修改 / `db.add(MemoryCursor)`）和 status 标记（`update status='processed'`）都在**同一个 db session、同一个 `db.commit()`** 内，SQL 事务保证原子——不会出现"游标推进但 status 没改"或"status 改但游标没推"的中间态。

> 标记为「指导者」外部检查。整体做得好——表结构符合折中版、聚合粒度正确、纯函数设计清晰、主动发现 commit 边界。

2. **聚合粒度正确**：`(scene_id, user_id)` 跨 agent，符合块 B 决策 2。

5. **主动发现 commit 边界 + 无游标纯函数**：提前识别块 B-2 要处理的问题。

### 需要澄清/注意的（3 个点）

**① scene_name 的稳定性（最重要，方案埋的隐患浮现）**：

`apply_scene_operations` 按 scene_name upsert（同名才 update，不同就 create），而 scene_name 由 LLM 自动命名。**隐患**：LLM 每次命名可能不一致——同一主题第一次命名"订单DH001退货处理"、第二次命名"DH001退货跟进"，名字不同 → 又 create → 同一主题拆成多个块，违背"深度整合"。

`aggregate_scenes` 接收了 `existing_blocks`（LLM 能看到已有块名），但**需确认 prompt 里是否有"优先 UPDATE、沿用已有块名"的约束**（对应 TencentDB 的"UPDATE 首选、CREATE 最后手段"）。若没有，块 B-2 要补上，否则 upsert 命中率低、场景块碎片化。

**② L2 增量游标的设计（块 B-2 要定）**：

日志说"L2 目前无游标纯函数，增量消费在块 B-2 做"。但 L2 游标用什么要定：方案写的是 L1 的 `updatedAfter`（updated 时间），而非 L1 自增 id。**关键要澄清**：L2 消费的"增量 L1"是"新产生的"还是"新产生 + 更新过的"？若只消费新产生 → 用 created 时间/id 即可；若还要消费去重 update 过的 → 用 updated 时间。方案写 `updatedAfter` 暗示后者，但"update 过的 L1 重新聚合"会不会重复聚合，需在块 B-2 明确。

**③ update 场景未验证（L2 核心还没测）**：

验证只覆盖 create（1 条记忆 → 新建块）。但 L2 的核心是"增量整合"——新记忆**融入已有块**（update/merge）。块 B-2 触发时需补"update 场景"验证：先有已有块，再来新记忆，验证 LLM 正确 update 而非又 create。

### 总结

P1-B-1 做得对。最需关注 **scene_name 稳定性**——upsert 依赖 scene_name 一致，但 LLM 命名可能每次不同，导致同一主题拆块。需确认 L2 prompt 是否有"优先 UPDATE、沿用已有块名"约束。另两点是块 B-2 要定的：L2 增量游标用 created 还是 updated、update 场景未验证。

### 需要澄清/注意的（1 个点，非紧急）

**L1 去重（merge）与 L2 增量消费的交互——"增量消费"模型的盲区**：

```
① L1 抽取记忆 A（seq_id=5）→ L2 消费 5，聚合 A 到场景块
② L1 抽取记忆 B（seq_id=6），去重发现 B 和 A 重复 → merge 成 A'（seq_id=7）
   （A 被删除/标记，A' 是"新记录"，含 A+B 的内容）
③ L2 消费 7，聚合 A'（A' 里又含 A 的内容）
   → A 的内容被聚合了两次（seq_id=5 一次，seq_id=7 的 A' 又一次）
```

**根源**：merge 产生的 A' 有**新的 seq_id**，L2 把它当"新产生"消费了，但 A' 含**已聚合过的 A 的内容**。

**为什么非紧急**：merge 频率通常低（大部分 L1 是 store）；即使重复聚合，LLM 深度整合会融合重复，后果是"浪费一次聚合 token"，不是"质量变差"。但要知道：**L2 的 seq_id 游标无法感知 L1 的 merge 血缘**。未来 merge 频率高或对 token 敏感时，需考虑"L1 merge 标记 L2 别重聚"或"L2 聚合时 memory_ids 去重"。


- ✅ 正确：插入冲突 → 捕获唯一约束异常 → **读回已有的 session_id**。

回填 `NULL → max(seq_id)` 的边界：若某组"有画像 + 有 active L1 + 但 L2 场景块还没聚合"（罕见），回填后这些 L1 的 seq_id <= last_seq_id，暂时不进 L3。但不是丢数据——等 L2 聚合出新场景、L1 有新记忆时重新触发。边界可接受。

### 总结

这次澄清回应质量很高：核实假象、发现真 bug、根因准确、修法正确、判断准确。两个补充：① 死循环不调 LLM、严重性低，但不改"应该修"的结论；② 回填 SQL 的罕见边界可接受。没有需进一步澄清的问题——分析和修法已到位。

## 指导者检查（P1-A-2 Kafka 改造）

> 标记为「指导者」外部检查。实现干净、采纳了之前的关键建议（幂等 record_id、统一 persist_l0、Kafka 只削落 L0）。但最大缺口是"验证"——只做了语法+import，没端到端验证，降级路径完全没测。

### 做得好的

1. **采纳了之前的关键建议**：幂等用 record_id + `ON CONFLICT DO NOTHING`（DB 唯一约束而非应用层查重）；抽统一 `persist_l0`（l0_store.py，两条路径都调它）；Kafka 只削落 L0、抽取走游标轮询。
2. **实现干净**：删了旧 `_batch_write_records`、旧 mq_consumer 同步抽取辅助、无用 import——没留旧代码。
3. **设计决策清晰**：Kafka 职责、抽取走游标、幂等、降级、消息格式——5 个决策明确。
4. **诚实标注剩余**：memory.result 暂未用、mock_extractor 死代码、Kafka 消息大小——不藏坑。

### 需要澄清/注意的（3 个点）

**① 端到端验证缺失——只有"语法+import"，没验证完整链路**：

Kafka 改造的核心链路 `write 投 Kafka → consumer 消费落 L0（幂等）→ L1 worker 游标轮询抽取` 完全没验证。需补：write 投 Kafka 是否成功、consumer 是否消费落 L0（幂等生效、record_id 不重复）、L1 worker 是否还能从 pending_extract 抽取（游标轮询不受 Kafka 影响）。这是开发日志的惯例（每任务都有"验证结果端到端"），这次缺了。

**② 降级路径完全没测——这是"两条写入路径"复杂度的核心**：

设计有"降级：Kafka 不可用 → write 降级同步落 L0"，但没验证。需补降级专项：停 Kafka → write（确认降级落 L0）→ L1 worker 低频轮询兜底 → 恢复 Kafka → 确认降级期数据不被重复落（幂等覆盖降级路径）。

**③ "批量 insert"是否真做了？persist_l0 描述没明确**：

设计说"consumer 批量 insert"，但 persist_l0 描述是"pg_insert ON CONFLICT DO NOTHING 幂等落库"，未明确"批量"。若单条 insert，"批量 insert"优化未做，落 L0 QPS 没优化，Kafka 削峰收益打折。需确认 persist_l0 是"攒批 insert"还是"逐条 insert"（批量 insert 是削落 L0 峰值的关键优化，属压测调优要补的）。

### 总结

Kafka 改造实现干净、采纳关键建议。但最大缺口是"验证"：① 端到端验证缺失（write→Kafka→consumer→L1 完整链路）；② 降级路径完全没测（两条写入路径复杂度的核心）；③ "批量 insert"是否真做需确认。建议先补端到端验证 + 降级专项验证，再确认批量 insert。

3. **迁移调用点全面**：5 处（search/context/store/dedup/session）都迁移到 vector_store，去桥接查询。
4. **asyncio.to_thread 包装同步 Qdrant 调用**：正确的并发实践（避免阻塞事件循环）。
5. **point id = UUID5(memory_id)**：确定性哈希，同一 memory_id 总是同一 point（insert 幂等），检索从 payload 拿 memory_id，无需桥接表。

### 需要注意的（2 个点）

**① 清空 collection 后存量向量丢失——生产需要"存量向量重建"迁移方案**：

日志诚实标注"存量记忆向量丢失，开发/测试环境可接受"。但生产部署时，清空重建 collection 后存量记忆（T_MEMORY 数据还在）的向量全没了，检索找不到存量记忆。需记录生产迁移待办——"存量记忆向量重建（reindex）：遍历 T_MEMORY 存量记忆 → embed → vector_store.insert"，这是存储抽象层改造的生产前提（类似之前 Kafka 迁移的"存量 L0 标记 processed"）。

**② 验证还是"import 通过"，缺端到端验证——比"后端补字段"影响更大**：

存储抽象层改造改了检索核心链路（search/context/dedup 三处查询逻辑 + 删桥接表 + 清空重建 collection），但验证只是"全量 import 通过"。需补端到端验证：写一条记忆 → 等 L1 抽取 → 调 search/context 检索 → 确认能搜到（memory_id 从 payload 拿正确、向量写入正常、UUID5 point id 检索命中）。这比"import 通过"能真正验证"存储抽象层改造没破坏检索"。

### 总结

存储抽象层 + 去桥接表设计正确（VectorStore 接口、UUID5 point id、迁移全面、asyncio 包装）。两个注意点：① 清空 collection 后存量向量丢失，生产需"存量向量重建"迁移方案（遍历 T_MEMORY 重新 embed+insert）；② 验证还是 import 通过，缺端到端验证——这个改动改了检索核心链路，比"后端补字段"更需端到端验证（写→检索闭环确认）。

## 指导者检查（2026-08-20 · 稀疏 64bit + L2 scene_name 归一化）

> 标记为「指导者」外部检查。本次两个改动：L2 scene_name 归一化**改对了**；稀疏词 ID「改 64bit」**改出严重 bug**——且这条「改 64bit」建议本身就是指导者给的错误建议，特此纠正。

### 严重问题：sparse 词 ID 改 64bit 超出 Qdrant 的 uint32 上限

证据链（三处核对一致）：

1. `sparse_encoder.py:16` 现为 `int(md5(word).hexdigest()[:16], 16)` → 64bit，最大值 `18446744073709551615`。
2. Qdrant sparse 索引类型是 **uint32**：`qdrant_client/proto/points.proto:130` 明确 `repeated uint32 indices = 2;`，上限 `4294967295`。
3. `md5[:8]`（32bit）最大值 = `2^32 - 1`，**恰好是 uint32 上限**；`md5[:16]`（64bit）约 99.99999997% 的值**超出** uint32。

**影响**：几乎每个词的词 ID 都超 uint32，`search_keyword` / `upsert` 的 sparse 向量序列化会报错（被 `except` 包成 `VectorStoreError`）或静默截断（截断则碰撞依旧，白改）。由于 `hybrid_search` 内部调 `search_keyword`，**hybrid 检索连带失效**。

**责任澄清**：指导者在《深入技术问题探讨.md》原建议是「改 64bit 或加冲突检测」——「改 64bit」这条是错的，没先确认 Qdrant sparse 索引是 uint32。开发者照做引入 bug，责任在指导者建议，不在开发者执行。

**正确处理**：
- **回退到 `md5[:8]`**。它已是 uint32 能表示的全部 32bit，**没有「更多位」可用**——碰撞风险是 Qdrant sparse 格式的**固有约束**，不是加位能解决。
- **降级严重性**：32bit 对 ~35 万词中文词表，生日碰撞约 14 对词共享一个 ID，实际影响（少量词对共享 IDF、偶发关键词误命中）很小。原「要改」是高估了，应降级为「已知限制记录在案」。
- 若将来实测碰撞造成问题，再考虑换非 Qdrant 的关键词索引（如独立 BM25 store），而不是在 uint32 里加位。

### L2 scene_name 归一化：改对了

`l2_scene.py` 实现正确：`SCENE_MATCH_THRESHOLD=0.75`、精确匹配优先、未命中才惰性批量算 embedding（`_load_block_embeddings`）、失败降级 create、归入时统一用已有块名（`scene_name = best_block.scene_name`）避免命名漂移。`embedding_client.embed_single/embed_batch` 方法均存在，引用有效。

### 缺失：本次改动无「验证」段

64bit 这个改动最需要验证——若当时跑 `_test_keyword_search.py` 就能立刻发现 sparse 索引越界。建议回退后补端到端验证：写「订单 DH001」→ `search_keyword("DH001")` → 确认不报错且字面命中。

### 结论

#4（scene_name 归一化）改对；#5（稀疏 64bit）改错，需**回退 `md5[:8]`** 并把「32bit 碰撞」从「要改」降级为「已知限制」。#1/#2/#3 暂缓合理，#1 已记待办。

## 2026-08-21 · session_time 校验兼容 Z 后缀

### 背景

### 改动

- `_validate_iso8601`：解析前 `normalized.replace("Z", "+00:00")`，兼容 Python < 3.11。

### 验证

`Z` 后缀、`+08:00` 时区均能正确解析，`standardize_timestamp` 正确转 UTC。

### 附带提醒

`session_time` 是「历史会话发生时间」，前端/清洗方不应 `toISOString()` 转换时区（会丢原始时区信息），应原样传 `+08:00` 格式。后端两种格式均兼容。
