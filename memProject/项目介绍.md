# 面向大模型智能体的记忆系统 — 项目介绍

> 本文为项目整体介绍，包含：项目简介、项目亮点、值得深入的问题、深入问题探讨四部分。
> 深入问题的详细解答见《深入技术问题探讨.md》。

---

## 一、项目简介

这是一个**独立、通用、可接口化调用的智能体记忆管理系统**，为各类大模型智能体提供统一的外部记忆能力，让它们在多轮、跨会话、多场景的交互中「记住」用户，实现连续、个性化的对话体验。

**解决的核心痛点**：大模型本身无状态，每次对话都从零开始。本系统在智能体和用户之间架设一层记忆层——对话中自动抽取有价值的记忆，下次对话前检索并注入上下文。

**能力闭环**：

```
接入写入 → 建模分层 → 生成去重 → 多路检索 → 上下文返回
```

**技术栈**：FastAPI + SQLAlchemy async + PostgreSQL(pgvector) + Qdrant + Kafka(KRaft) + Docker；LLM 用 DeepSeek，Embedding 用 SiliconFlow BGE-M3(1024 维)。

**多智能体与隔离**：以「智能体 → 场景 → 数据」为隔离链，通过 `user_id / scene_id / agent_id` 三维归属 + `memory_scope`（user/session/task/agent）四级复用边界 + `spaces.yaml` 身份映射，支撑多智能体、多场景、多用户共存的记忆隔离与共享。

**当前状态（诚实）**：核心链路（写入/抽取/去重/检索/上下文）已闭环，但仍有未完成项——仅 Qdrant 一种向量实现、去重与检索无评测集、L3 画像刚起步、无压测验证。

## 二、项目亮点

1. **四层记忆分层（L0→L1→L2→L3）**
   对话是零散、冗长的，直接原样存进去既占空间又难以复用。系统把记忆像「矿石提炼」一样层层加工：**L0** 原始对话（完整可追溯）→ **L1** 原子记忆（抽取出的单条事实/偏好/任务状态）→ **L2** 主题场景块（把相关记忆聚合成有叙事的块）→ **L3** 长期画像（稳定的用户特征）。每层服务不同目的：底层负责可追溯、可解释，上层负责跨会话长期复用。

2. **Kafka 削峰 + 游标轮询的写读分离**
   记忆抽取要调大模型，单次耗时秒级，如果写入时同步等结果，高并发下接口会卡死甚至丢数据。系统的做法是：**写入只把对话投进 Kafka 立刻返回**（毫秒级），后台消费者先落原始对话，再由独立的 L1 worker 用一个「落库游标」增量扫描、逐批抽取。游标只有在成功后才推进，失败就下轮重试，配合记录级幂等键，保证「不丢、不重」，设计上支持高吞吐写入（横向扩展能力未经压测验证）。

3. **存储抽象层（设计前瞻）**
   为避免业务代码被某一家向量库锁死，系统定义了统一的 `VectorStore` 接口，业务层只跟抽象打交道。当前仅 Qdrant 一个实现（换库路径尚未真正验证），接口已预留；同时把 `memory_id` 直接当作向量索引 ID、去掉桥接表，减少一层 join 和不一致风险。

4. **hybrid 混合检索（RRF 融合）**
   单靠语义检索有个经典盲区：用户问「DH001 这个订单」，语义向量可能匹配不到这条精确编号；反过来纯关键词又查不到「想退货」这种换了个说法的同义表达。系统用**双路召回**：dense 向量捕捉语义相似，sparse 关键词捕捉字面精确，再用 Reciprocal Rank Fusion 把两路结果按排名融合，两类查询都能命中。

5. **多信号去重融合**
   用户反复聊同一件事，如果不做处理，记忆会越存越多、越来越脏。系统对每条新记忆和库里已有记忆做**三路信号比对**——向量相似度、关键词重合度、标识一致性（是不是同一用户/同一任务），加权后决定是「新增、合并、更新、还是丢弃」。既避免冗余膨胀，又通过版本历史表保留每次变更前的旧内容，记忆的演化过程可追溯。

6. **透明代理（零改动接入）**
   想让外部已有的智能体（比如 Claude Code、DeepSeek harness）用上记忆能力，最理想的方式是「它们一行代码都不用改」。系统提供了一个 OpenAI 兼容的 `/chat/completions` 端点，外部智能体照常发请求，代理在中间自动完成三件事：**召回记忆注入上下文 → 转发给真正的大模型 → 把本轮对话异步写回记忆库**。身份映射在配置文件里预先写好，外部完全无感知。

## 三、值得深入的问题（已解决）

1. **海量写入如何不阻塞、不丢、不重？** → Kafka 削峰 + 游标轮询 + record_id 幂等。
2. **检索如何兼顾语义召回与字面精确召回？** → 三路检索架构，落地为 dense+sparse 的 hybrid + RRF 融合。
3. **向量库未来可能更换，如何不锁死厂商？** → 存储抽象层 + 去桥接表。
4. **重复/相似记忆如何避免记忆库膨胀？** → 多信号去重融合决策矩阵 + 版本历史可追溯。
5. **外界智能体如何低成本接入？** → 透明代理，OpenAI 兼容协议 + spaces.yaml 身份映射。
6. **记忆该在多大范围内复用（用户级/会话级/任务级）？** → memory_scope 推导 + scene_id 隔离，双维度正交。

## 四、深入问题探讨（9 个方向）

> 以下是针对核心实现提出的 9 个深入方向，详细解答见《深入技术问题探讨.md》。各方向一句话结论如下：

1. **记忆抽取为什么「一次调用」而不是「分类一次 + 抽取一次」？**
   → 当前实为两阶段（extract + generate）；「分类」和「内容抽取」是同一认知动作、拆开成本翻倍；结构化 JSON 天然支持一次输出多类。此为成本/延迟/工程常识决策，非 A/B 测试驱动。

2. **如何保证输出结构符合预期、结果可控？**
   → 五道关卡：prompt 软约束 → API 硬约束（JSON mode）→ 解析容错 → 字段校验 → 价值过滤。

3. **L2 聚合、L3 画像与游标设计？**
   → 游标是 `t_memory_cursor` 表（cursor_key + last_processed_id），记录「上次处理到哪」，增量消费、失败不推进。L2 一次 LLM 把 L1 聚成主题场景块（update/create/merge）；L3 攒够 N 条新 L1 后把变化场景凝练成画像。

4. **Kafka 如何保证可靠与幂等？**
   → 生产端 `acks=all`；消费端手动 commit + `record_id` 唯一约束 + `ON CONFLICT DO NOTHING`；失败指数退避重试 3 次后进 DLQ。

5. **存储层抽象怎么做、为什么？**
   → `VectorStore` 抽象接口（insert/search/search_keyword/hybrid_search/delete），Qdrant 实现 point id=UUID5(memory_id)、无桥接表；为隔离向量库选型变化。

6. **混合检索怎么做？**
   → dense（BGE-M3 语义）+ sparse（jieba 词频 + Qdrant IDF）双路召回，RRF（k=60）按排名融合，上层再叠加新近性/重要性/置信度加权。

7. **L1 去重怎么做、如何评判、测试？**
   → 向量找相似 → LLM 批量判断四动作（keep_new/merge/update_existing/discard）→ 应用+审计+调权。审计表留痕可离线分析；**当前无专门的效果评测脚本**（明确空白）。

8. **为什么需要代理？**
   → 让外部已有智能体零改动接入，OpenAI 兼容端点 + spaces.yaml 身份映射，代理自动完成召回注入→转发→写回。

9. **memory_scope 层级推断的可靠性？**
   → **关键澄清**：`memory_scope` 是代码推断（非模型推断），由 `_infer_scope` 按「有无 task_id/session_id」机械决定；`session_id` 是写入时上游传入的，不是模型生成，故层级可靠性取决于接口契约而非模型。

## 五、指导者评价（2026-08-20）

> 核对方式：把本文论断逐个对着代码验证（VectorStore 实现数、worker 并发控制、tests 目录、压测脚本、稀疏编码等），非凭印象。

### 简介部分

「一句定位 + 痛点 + 闭环 + 技术栈」很干净，但缺两个关键维度：

1. **没讲「多智能体/隔离」这个核心身份**。`user_id/scene_id/agent_id` 隔离模型、`memory_scope` 四级、`spaces.yaml` 身份映射——这些才是本系统区别于「普通 RAG 记忆」的东西。简介和亮点都在讲单租户能力，读者看不出这是个多租户多智能体系统。
2. **没讲成熟度**。亮点读完会以为系统完备，但实际只有一种向量库、去重/检索无评测、L3 刚起步。应补一句「当前状态 / 未完成项」。

### 亮点逐个判定

| # | 亮点 | 判定 | 依据 |
|---|---|---|---|
| 1 | 四层记忆分层 | ✅ 真 | 核心架构，有实质 |
| 2 | Kafka 削峰+游标 | ✅ 真，但带**未验证宣称** | 「日均百万级」全仓无压测脚本支撑 |
| 3 | 存储抽象层 | ⚠️ **半真半凑** | 接口真实，但只有 `QdrantVectorStore` 一个实现，「可替换/迁移 Oracle」是愿景非现状 |
| 4 | hybrid 混合检索 | ✅ 真 | dense+sparse+RRF 已实现 |
| 5 | 多信号去重 | ✅ 真 | 三信号+四动作+版本追溯 |
| 6 | 透明代理 | ✅ 真 | 零改动接入，实际有价值 |

**结论**：4 真、1 半（#3）、1 真但带未验证宣称（#2）。不算堆砌，但有两处应改：

- #2 的「能扛住日均百万级写入」→ 改成「设计上可横向扩展」或补注「未经压测验证」。
- #3 的「可替换向量库」→ 改成「为未来换库预留接口（当前仅 Qdrant 实现）」，从「亮点」降级为「设计前瞻」更诚实。
