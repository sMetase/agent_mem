# 记忆系统深入技术问题探讨

> 本文记录对记忆系统核心实现的深入追问与解答，覆盖抽取、结构控制、分层聚合、Kafka、存储抽象、混合检索、去重、代理、会话隔离九个方向。
> 编写日期：2026-08-20。

---

## 1. 记忆抽取为什么「一次调用」而不是「分类一次 + 抽取一次」

**问题**：为什么不先调一次模型专门做记忆分类，再调一次模型按类抽取内容，而是直接一次模型调用就把五类记忆抽出来？是做了什么测试，还是出于什么考虑？

**回答**：

先纠正一个前提——当前实现**并不是一次调用就完事，而是两阶段**：

- **extract（第 1 次调用）**：一次调用同时抽五类。分类字段（`key_facts`/`task_state`/`preferences`/`process`/`feedback`）和内容字段在**同一个 JSON 里一起输出**，每条碎片带一个 `value` 评分（`memory_extractor.py:160-235`）。
- **generate（第 2 次调用）**：把碎片标准化成正式记忆（`content`/`summary`/`importance`/`confidence`）（`memory_generator.py:67-141`）。

所以「分类 + 内容」确实合并成一次了，但「粗提取」和「精加工」是分开的。

为什么不把「分类」和「内容抽取」拆成两次：

1. **它们是同一个认知动作，拆不开**。让模型「识别这段话里有哪些记忆、各是什么类型」和「把这些记忆的内容写出来」是同一次理解过程。硬拆成两次意味着第二次要重新读原文、重新定位内容，而且第一次的分类结论和第二次的抽取内容可能**对不齐**（第一次说「有偏好」，第二次抽出来的却对不上）。

2. **成本/延迟翻倍**。原文要传两遍、token 两倍、往返两倍。日百万级数据下这是实打实的钱和时间。

3. **结构化 JSON 天然支持一次输出多类**。一个 JSON 里五个字段，字段名就是分类、字段值就是内容、`value` 就是评分，一次响应全拿到。这是 LLM 结构化输出的成熟用法。

4. **真正的分工点选在「抽取 vs 生成」**，而不是「分类 vs 内容」——后者是更没价值的分法。

**诚实说明**：没有专门做「一次抽取 vs 分类+抽取两次」的 A/B 测试。这是基于成本、延迟和 LLM 实践常识做的设计决策，不是实测数据驱动的。

## 2. 如何保证输出结构符合预期、结果可控

**问题**：为了保证记忆输出符合预期，是给提示词做了强制要求对吗？后面怎么做的，怎么保证结果可控？

**回答**：「prompt 强制要求」只是第一道（软约束），后面还有四道硬关卡，层层兜底：

1. **Prompt 软约束**：system prompt 写死输出结构 + `output_schema`（JSON Schema）。
2. **API 硬约束**：`response_format={"type":"json_object"}`，让 DeepSeek/OpenAI 的 JSON mode 在 API 层强制返回合法 JSON（`llm_client.py:139`）。
3. **解析容错**：`json.loads` → 失败则 regex 提取 JSON 块 → 仍失败抛 `LLMServiceError`（`llm_client.py:142-162`）。
4. **字段校验**：`MemoryCandidate.validate()` —— 类型白名单（非法降 `fact`）、值域截断（importance/confidence 截到 [0,1]）、空值兜底（summary 用 content 前 200 字）（`memory_generator.py:43-53`）。
5. **价值过滤**：`_filter_value` —— `value < 0.3` 的碎片直接丢弃（`memory_extractor.py:26-30`）。

最终落库的，一定是符合 schema 定义的合法记忆。

## 3. L2 聚合、L3 画像与游标设计

**问题**：L2 的聚合和 L3 的画像说得很不清楚，而且没有解释什么是游标、有什么用、怎么设计的。

**回答**：

### 3.1 游标（cursor）

- **是什么**：数据库表 `t_memory_cursor`，就两列——`cursor_key`（主键字符串）+ `last_processed_id`（BigInteger，最后处理到的自增 id）。
- **为什么需要**：worker 是「定时轮询」模式，不是「推」模式。每次醒来要回答一个问题——「上次处理到哪了？这次从哪继续？」游标就是记住这个位置。没有它，要么全量重扫（浪费），要么丢增量。
- **怎么设计**（三种 worker 各一套）：

| worker | cursor_key | 游标值 |
|--------|-----------|--------|
| L1 | `user_id:agent_id:session_id` | L0 记录自增 id（`InteractionRecord.id`） |
| L2 | `l2:scene_id:user_id` | L1 最大 `seq_id`（`Memory.seq_id`） |
| L3 | 不单独建表 | 用 `t_persona.last_seq_id` 字段当游标 |

- **核心机制**（读→处理→推进，失败不推进）：
  1. 读增量：只查 `id > 游标` 的新记录
  2. 处理这批
  3. 成功 → 游标推进到本批最大 id
  4. 失败 → 游标不动，下轮重试同一批（保证不丢）

- **和 Kafka 的分工**：Kafka 只负责「落 L0 削峰」，抽取/聚合/画像都走 DB 游标轮询——因为这几个步骤要**按 (user/agent/session) 分组、批量、可重试**，用游标 + 轮询比 Kafka 消费更简单可控。

### 3.2 L2 聚合（6 步）

1. 每 10s 醒来，查出有 active L1 记忆的 `(scene_id, user_id)` 组（`l2_worker.py:32-41`）。
2. 每组读「seq_id > 游标」的新 L1（最多 50 条）+ 该组已有场景块。
3. **一次 LLM 调用**：输入「新记忆 + 已有块」，输出 `operations`（`l2_scene.py:44-82`）。
4. 三种操作：
   - `update`（优先）：新记忆归入已有主题 → 深度重写叙事，`scene_name` 必须与已有完全一致
   - `create`：全新主题 → 新建块
   - `merge`：串起多块 → 合并（`merged_from` 列出被合并块）
5. `scene_name` 由 LLM 在 user 范围内自动命名，作为「主题」标识。
6. 落 `t_scene_block`（PG 存叙事全文），推进游标。

### 3.3 L3 画像（5 步）

1. 每 15s 醒来，对每个 `(scene_id, user_id)` 数「自上次画像以来新增 L1」（`l3_worker.py:44-61`）。
2. 触发条件：`新增 L1 ≥ 5` 条（`L3_TRIGGER_N=5`）。
3. 满足则读「变化场景」（`updated_at > last_persona_time`），无变化跳过（`l3_persona.py:46-60`）。
4. LLM 从场景块叙事**凝练**出画像（跨场景稳定特质，2000 字内，禁止臆测）。
5. 存 `t_persona`，更新 `last_persona_time` + `last_seq_id`。

一句话：**L2 把「点」串成「线」（主题叙事），L3 把「线」抽象成「面」（长期画像），都是增量 + LLM 凝练，逐层从具体到抽象。**

## 4. Kafka 可靠性与幂等

**问题**：Kafka 怎么保证消息可靠、怎么保证幂等消费、相关参数怎么设置的。

**回答**：

### 可靠性（生产端 `mq_producer.py:47-57`）
- `acks="all"` —— 所有 ISR 副本确认才认为投递成功
- `compression_type="gzip"`、`max_request_size=1MB`
- `linger_ms=5`（攒批）、`request_timeout_ms=5000`
- 投递带 5s 超时，失败返回 `False`，上层走「降级同步落 L0」（`memory.py:209`）

### 幂等（消费端 `mq_consumer.py` + `l0_store.py`）
- `enable_auto_commit=False` —— **手动提交 offset，只有处理成功才 commit**（`mq_consumer.py:63, 117`）
- 核心幂等靠 `record_id` 唯一约束 + `ON CONFLICT DO NOTHING`（`l0_store.py:158-162`）。`record_id` 是 write 侧**预生成**随消息传递的，同一批消息被重复投递/重复消费时落库自然跳过。

### 消费参数（`mq_consumer.py:56-67`）
- `group_id=memory-system`、`auto_offset_reset=earliest`
- `max_poll_interval_ms=300000`（处理可以慢）
- `session_timeout_ms=30000`、`heartbeat_interval_ms=10000`

### 重试
- `max_retries=3`，指数退避 `1000ms * 2^attempt`
- 3 次仍失败投 DLQ（`memory.dlq`），**失败也 commit**（避免毒消息卡死后续）

> 语义是「至少一次」(at-least-once)，靠 record_id 幂等兜底达成「恰好一次」的效果。

## 5. 存储层抽象

**问题**：存储层抽象怎么做、为什么要抽象。

**回答**：

定义 `VectorStore` 抽象基类，5 个方法（`vector_store.py:40-88`）：
```
insert / search(语义) / search_keyword(关键词) / hybrid_search / delete
```

`QdrantVectorStore` 是当前实现（`vector_store.py:91-169`）：
- **point id = UUID5(memory_id)**，确定性映射，不是随机 id
- payload 存 `memory_id` + `user_id` 等元数据
- **无桥接表**：检索直接返回 memory_id 回查 PG

**为什么**：向量库选型会变（现在 Qdrant，未来可能 Oracle 23ai，向量+关系同表）。业务层只依赖 `VectorStore` 接口，换库只需新增一个实现类，业务代码一行不改。抽象的价值就是**隔离变化**。

## 6. 混合检索细节

**问题**：混合检索怎么做，说具体。

**回答**：

### 写入侧（每条记忆落库时生成两个向量）
- **dense**：content 用 BGE-M3 编码成 1024 维浮点向量
- **sparse**：content 用 jieba 分词 → 词频统计 → 词用 md5 前 8 位转成 uint32 词 ID → `{词ID: 词频}` 稀疏向量（`sparse_encoder.py`）
- 两个向量一起 upsert（named vectors：`""` 存 dense、`keyword` 存 sparse）
- collection 配置：dense 用 COSINE，sparse 用 `SparseVectorParams(modifier=IDF)`（检索时自动 IDF 加权，即轻量 BM25）

### 检索侧（query 进来）
1. query 同样做 dense 向量化 + sparse 稀疏化
2. **dense 路**：`query_points` 用 dense 向量搜，COSINE 相似度，按 user_id 过滤，取 top_k
3. **sparse 路**：`query_points` 用 sparse 向量搜（`using="keyword"`），IDF 加权，取 top_k
4. **RRF 融合**（`_rrf_fusion`，`RRF_K=60`，`vector_store.py:24-37`）：
   ```
   每条记忆 score = 1/(60+dense排名+1) + 1/(60+sparse排名+1)
   ```
   再归一化到 [0,1]，按分数取 top_k
5. **上层再排序**（`memory.py:353-358`）：
   ```
   最终分 = hybrid_score*0.6 + recency*0.15 + importance*0.15 + confidence*0.1
   recency = 0.5^(age_days/30)   // 时间衰减
   ```

**举例**：query=`DH001` —— dense 路语义泛化可能排不到精确订单，但 sparse 路 jieba 切出 `DH001`、词 ID 精确命中、排第一，RRF 融合后这条就浮上来了。

## 7. L1 去重逻辑

**问题**：L1 去重怎么做、怎么评判效果、做了什么测试。

**回答**：

### 流程（`memory_dedup.py`，v3 单层去重）
1. **Step1 找相似**：每个候选 → 向量搜相似（top_k=50, threshold=0.5）→ 拿到最像的已有记忆
2. **Step2 LLM 批量判断**：所有候选 + 各自相似记忆打包成**一次 LLM 调用**，批量判断动作
3. **Step3 应用**：应用决策 + 机械兜底 + 写审计 + 调权

### 四动作语义（边界是关键，`memory_dedup.py:308-342`）

| 动作 | 语义 | 例子 |
|------|------|------|
| `keep_new` | 全新 / 不同维度（都成立不矛盾） | 已有「喜欢咖啡」，新「喜欢茶」→ 两条都留 |
| `merge` | 同一事实的补充细节，不改原取值 | 「退款3天」+「用户已电话咨询」 |
| `update_existing` | 同一事实取值矛盾，最新为准 | 「退款3天」→ 实际「7天」 |
| `discard` | 语义完全覆盖、无新信息 | 「用户偏好咖啡」vs「用户喜欢喝咖啡」 |

### LLM 失败兜底（机械规则，`memory_dedup.py:145-156`）
- 向量分 `≥0.95` → discard
- `≥0.7` → merge
- 否则 keep_new

### 评判效果
- **审计留痕**：写 `t_dedup_audit`（候选/匹配/动作/融合前后内容），可离线统计误合并率
- **动态调权**：被 merge/update 的记忆 `importance/confidence +0.05`、`use_count+1`；被 discard 的 `use_count+1`（`memory_dedup.py:510-546`）

### 测试现状（诚实说明）
**目前没有专门的去重效果评测脚本**（没有准确率/召回率/误合并率的自动化测试）。`tests/` 目录基本为空，验证靠冒烟测试 + 专项测试，去重效果主要靠审计表事后观察。这是一个明确的空白。

## 8. 为什么需要代理

**问题**：为什么需要代理，做代理是为了什么。

**回答**：核心就一句——**让外部已经存在的智能体零改动接入**。

外部智能体（Claude Code、DeepSeek harness 等）不会为了用记忆系统去改自己的代码。代理提供 **OpenAI 兼容的 `/chat/completions` 端点**，外部照常发请求即可。代理内部自动完成（`proxy.py:239-283`）：

```
空间身份映射(space_id → user/agent/scene/api_key)
  → 提取 sessionKey 建会话
  → 召回记忆注入上下文
  → 转发真正的大模型
  → 异步写回本轮对话
```

身份、会话、场景对调用方**完全透明**，由 `spaces.yaml` 预配 + header 自动补全。

## 9. memory_scope 层级推断的可靠性

**问题**：你说由 memory_type 推断是 session 还是 task，那么模型推断出是 session 会给出一个 sessionId 吗？有模型判断层级，怎么保证可靠？

**回答**：

**这里有一个关键误解需要澄清：`memory_scope` 不是模型推断的，是代码推断的，100% 确定。**

- `memory_type`（fact/preference/task_state/process/correction 五类）= **模型判断**
- `memory_scope`（user/session/task/agent 四档）= **代码判断**（`memory_service.py:343-352` 的 `_infer_scope`）

代码规则：
```python
有 task_id                    → "task"
有 session_id（无 task_id）    → "session"
都没有                        → "user"
"agent"                       → 只能显式指定
```

**`session_id` 不是模型给出的，是写入时上游传入的**（`write` 接口 `session_id` 必填），L0 记录带着它，L1 抽取时原样继承（`l1_worker.py:98-105`）。所以：

- 模型**不会**「推断出是 session 然后给一个 sessionId」
- 层级可靠性**不取决于模型**，取决于上游是否正确传了 `session_id`/`task_id`——这是接口契约问题，不是模型可靠性问题

### 会话隔离（两个窗口共享记忆 vs 干净上下文）

- **共享机制**：记忆归属由 `user_id / scene_id / session_id / task_id` 决定。同 user 的两个会话，user 级、scene 级记忆会共享；`session_id` 不同的记忆天然隔离（`memory_scope=session`）。
- **当前实际**：L1 自动抽取的记忆 scope 推断为 `session`（或 `task`），所以大部分记忆本来就是会话级隔离；但代理注入时特意只召 `preference + fact` 且不传 `session_id`（`proxy.py:159`），所以偏好和事实跨会话共享。
- **想要干净上下文的手段**（`memory.py` 的 search/context 都支持）：
  1. 传 `session_id` 过滤：只召回本会话记忆
  2. 传 `memory_types` 过滤：只要 preference/fact，排除 task_state/process/correction
  3. 换 `user_id` 或 `scene_id`：彻底隔离
- **设计取舍**：系统默认「同 user 共享偏好/事实，会话/任务细节隔离」。若需「同 user 两个窗口完全隔离」，当前还缺一个「会话级隔离开关」——检索默认命中该 user 下所有 active 记忆，`session_id` 只是可选过滤，不是强制的。这是一个可再讨论的点。

**共性问题**：这些「深入问题」偏 **how（实现怎么做）**，而非 **why/risk/tradeoff（为什么这么选、放弃了什么、边界在哪）**。真正「深入」的是 #3/#7/#9；#5/#6/#8 在复述实现而非探讨。

### 未覆盖、但真实存在的问题（已从代码验证）

1. **L1/L2/L3 worker 是单实例假设，无分布式锁**（最该补）。`l1_worker.py` 并发控制只有 `asyncio.Semaphore(25)`（单进程内协程限流），游标「读→处理→推进」无 `FOR UPDATE`/Redis 锁。横向起多个 worker 实例会重复消费同一批。建议补：加分布式锁 / 游标抢占（`FOR UPDATE SKIP LOCKED` 或 Redis SETNX），或明确声明「当前单实例部署」。
2. **存储抽象「够不够抽象」未验证**。hybrid 的 sparse/IDF modifier 是 Qdrant 特有语义，pgvector/Oracle 23ai 未必有等价物——现在只有一种实现，等于没测过「换库」路径。
3. **检索质量无评测**。#6 的上层权重 `0.6/0.15/0.15/0.1`、`recency=0.5^(age/30)` 是拍脑袋定的，无 recall@k/NDCG 支撑；应补一个检索评测集（项目里已有 40 题/24 条场景数据可复用）。
4. **L2 的 `scene_name` 由 LLM 自动命名，稳定性存疑**。merge 依赖「scene_name 与已有完全一致」，但 LLM 对同一主题可能措辞不同 → 本该 merge 的 create 成新块。建议：scene_name 归一化（去空白/大小写）后再比对，或用 embedding 相似度做 merge 判定而非字符串全等。
5. **稀疏词 ID 用 md5 前 8 位 → uint32，有碰撞风险**。#6 的词转 uint32 方案，中文词表大、8 hex=32bit，碰撞概率非零，会导致不同词映射到同一词 ID、检索错误加权。低概率但真实，建议改 64bit 或加冲突检测。
