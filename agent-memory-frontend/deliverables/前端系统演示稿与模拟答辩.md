# 智能体记忆系统前端演示稿与模拟答辩

> 适用角色：前端系统演示人员
>
> 演示重点：前端页面、交互、接口联调、状态反馈和完整业务链路
>
> 当前版本检查：`pnpm check` 已通过，9 个测试文件、37 项测试通过，生产构建通过；构建仅保留既有的大分块提示。

## 一、先记住三句话

演示开始前，先把系统定位说清楚：

1. 这是面向多智能体业务的记忆管理控制台，不是实时 AI 聊天窗口。
2. 本次演示主线是“接入配置 → 数据校验与写入 → 记忆生成与去重 → 记忆管理 → 检索 → 上下文返回 → 运行监控”。
3. 前端负责把用户操作、请求参数、加载状态、错误状态和后端真实结果完整呈现出来；记忆抽取、向量检索、去重融合等算法由后端服务执行，前端不伪造结果。

建议全程使用“前端展示后端返回的真实结果”这句话。它既能说明前端工作，也能避免把后端算法效果误说成前端实现。

## 二、演示前准备

### 1. 环境和浏览器

- 建议使用 1280px 以上宽度，浏览器全屏，提前关闭无关标签页。
- 当前交接文档中的前端地址是 `http://120.27.207.238:8002/`，后端地址是 `http://120.27.207.238:8000`。如果现场地址不同，以实际部署地址为准。
- 现场先打开“系统设置”，确认 Base URL、User ID 和 Scene ID，不要在演示中临时猜地址。
- API Key 不要在投影、截图或口头答辩中完整展示。

### 2. 推荐使用的隔离演示数据

为了避免污染正式数据，建议使用一个临时 User ID：

| 字段 | 建议值 | 用途 |
| --- | --- | --- |
| User ID | `frontend_demo_日期` | 隔离本次演示数据 |
| Scene ID | `teacher-demo` | 标识委员会演示场景 |
| Task ID | `task_cold_chain_demo` | 串联任务过程、生成、记忆管理和上下文 |
| Agent 名称 | `冷链调度演示智能体` | 注册接入身份 |
| 导入文件 | [课堂演示-记忆导入测试.json](E:\memory_frontend\deliverables\课堂演示-记忆导入测试.json) | 一条包含偏好、事实、任务和约束的综合样例 |

如果后端已经准备好专用数据，也可以使用 `logistics-test` 和 `log_route_001` 等测试数据，但要保证 User ID、Scene ID 和 Task ID 的范围一致。

### 3. 演示前检查顺序

1. 在“基础连接设置”保存 Base URL。
2. 在“本地用户身份”保存隔离 User ID。
3. 在“场景标识配置”确认或创建 Scene ID。
4. 在“智能体注册接入”确认或注册 Agent，随后到“接口密钥配置”保存 Agent ID 和 API Key。
5. 打开“接口健康检查”，确认后端服务、版本和本次耗时可返回。
6. 打开“系统总览”，确认页面能加载真实数据或明确空态。
7. 如果要执行写入、生成或删除，先确认当前 User ID 是隔离用户，并准备好演示结束后的清理方案。

系统左侧导航保留了系统文档要求的七组功能。部分子入口共用一个真实工作台，通过路径或查询参数加载不同预设，因此不需要把同一套页面重复开发多次。

| 功能组 | 前端入口 | 演示时要覆盖的内容 |

| 1. 智能体接入与记忆数据写入 | 智能体注册、场景、密钥、数据导入、数据校验 | 身份配置、JSON/CSV 解析、三类写入、校验预览 |

| 6. 接口与运行监控 | 健康、调用状态、联调记录 | 健康检查、API 日志、检索日志、失败记录、权限空态 |

## 四、推荐的完整演示稿

下面的“口播”可以直接照读；“操作”是屏幕上的实际动作。整套建议控制在 15 至 20 分钟。

### 0. 开场定位：约 40 秒

**操作：** 打开系统首页，先不要急着点击菜单。

**口播：**

> 各位老师好，我今天负责展示的是面向多智能体业务的记忆管理控制台前端。这个系统解决的不是实时聊天，而是把智能体产生的对话、历史会话和任务过程沉淀为可管理、可检索、可返回给智能体的记忆。
>
> 今天我以一个冷链物流调度场景为例，使用一个 User ID、一个 Scene ID、一个 Agent ID 和一个 Task ID，按照系统实际功能链路完成一次端到端演示。演示重点放在前端页面、交互、接口调用和结果反馈；记忆抽取、检索和去重算法使用后端真实返回结果。

### 1. 系统总览：约 1 分钟

**操作：** 停留在“系统总览”，点击刷新数据。

**讲解顺序：**

1. 先看五张指标卡：接入智能体、业务场景、记忆总量、近 24 小时检索调用、上下文返回成功率。
2. 再看功能总览流程：接入与写入、多层记忆管理、上下文返回。
3. 下方查看智能体接入记录、记忆类型分布、近 7 天记忆趋势、上下文预览、当前状态和历史告警。

**口播：**

> 首页承担的是运行概览，不承载具体业务操作。这里的指标优先来自后台统计、Dashboard 聚合和真实日志接口。当前接口没有返回的字段，页面会显示“暂无统计”或空态，而不会拿当前分页样本推算全局比例。这样首页数据口径是可解释的。

**演示要点：**

- 如果卡片显示“暂无统计”，直接说明这是后端未提供该聚合字段，不要临时解释成前端故障。
- 如果智能体列表或上下文预览为空，说明当前 Dashboard 没有返回对应记录，随后用具体业务页面展示真实操作。

### 2. 连接、用户、场景和智能体接入：约 2 分钟

#### 2.1 基础连接和用户身份

**操作：** 进入“系统设置 → 基础连接设置”，确认 Base URL；再进入“系统设置 → 本地用户身份”，填写隔离 User ID。

**口播：**

> 这里配置的是当前浏览器使用的后端地址和 User ID。User ID 会参与记忆写入、列表、检索、上下文和任务请求，用于隔离不同用户的记忆范围。配置由 Zustand 统一管理，并保存到当前浏览器，页面之间不会各自维护一份连接配置。

#### 2.2 场景标识

**操作：** 进入“场景标识配置”，确认 `teacher-demo`；如果现场没有该场景，则输入场景名称和说明，点击“创建并启用场景”。

**口播：**

> Scene ID 表示业务场景边界。比如冷链物流、客服和运维可以使用不同的 Scene ID，避免不同业务场景的记忆混在一起。创建成功后，前端会把后端返回的 Scene ID 回填并保存为当前启用场景。

#### 2.3 智能体注册和凭据

**操作：** 进入“智能体注册接入”，填写智能体名称、Scene ID，选择读取和写入权限；如果已有 Agent，则只展示当前接入身份。必要时进入“接口密钥配置”保存或轮换 API Key。

**口播：**

> Agent ID 区分记忆的生产者或调用方，API Key 作为接口调用凭据。注册成功后，前端保存后端返回的 Agent ID 和 API Key，并在后续 Axios 请求中通过 `X-API-Key` 请求头发送。这里的凭据只保存在当前浏览器，实际生产环境还需要结合 HTTPS、管理员认证和更安全的密钥托管策略。

### 3. 数据校验与记忆写入：约 3 分钟

#### 3.1 浏览器侧数据校验

**操作：** 进入“数据校验与标准化”，上传 [课堂演示-记忆导入测试.json](E:\memory_frontend\deliverables\课堂演示-记忆导入测试.json)。

**屏幕上展示：** 已识别记录、结构校验状态、场景/任务字段覆盖率、标准化结果预览表。

**口播：**

> 这里先不写后端，只在浏览器中解析 JSON 或 CSV。前端检查文件格式、记录是否为对象、是否有可转换内容，以及 role 是否属于 user、assistant、system，并把结果标准化后预览。它是写入前的快速反馈，最终的数据合法性仍由后端接口负责。

#### 3.2 对话记录写入

**操作：** 进入“记忆数据导入”，保持“对话记录”，选择同一文件，确认解析条数，点击“校验并写入”。

**口播：**

> 当前模式把每条记录映射为一条 dialogue 写入请求，包含 User ID、Scene ID、Task ID 和 messages。前端按顺序处理记录，避免一次性发起无上限并发；提交期间按钮会进入加载状态，防止重复写入。完成后页面显示成功处理数量、生成结果数和最近导入批次。

#### 3.3 历史会话和任务过程

**操作：** 将上方 Segmented 控件切换为“历史会话”和“任务过程”，分别展示模式说明和字段映射；时间允许时各提交一条测试记录。

**口播：**

> 这三个入口共用同一个导入工作台，但写入载荷不同：对话模式使用 messages，历史会话模式使用 session summary、时间和来源，任务过程模式使用 task goal、progress 和 result。前端先统一解析输入，再根据模式构造对应 payload，最终调用真实的 `/api/v1/memory/write`。

**必须说明：**

- 页面上的导入统计是当前浏览器、当前用户的本地活动统计，不代表后端全局统计。
- 如果导入过程中部分记录成功、后续记录失败，页面会标记“部分完成”，不会把整批误报为成功。

### 4. 任务过程管理：约 1 分钟

**操作：** 进入“任务过程管理”，点击“创建任务”，填写：

- 任务标题：`济南冷链路线优化`
- 任务目标：`在指定日期前完成冷链调度方案并完成接口联调`
- 场景 ID：当前 Scene ID

创建成功后，点击“查询进度”；再点击“更新进度”，设置状态为“进行中”，填写已完成项和待办项。

**口播：**

> 任务页把长周期任务的目标、状态、完成项和待办项集中管理。创建后前端保存 Task ID，并使用真实进度接口刷新已完成项、待办项和关联记忆数。后续导入、生成、检索和上下文请求都可以携带这个 Task ID，实现任务范围内的记忆关联。

### 5. 记忆生成与去重融合：约 4 分钟

#### 5.1 单条同步生成

**操作：** 进入“生成与去重融合”或“关键事实提取”预设。输入一条包含事实和约束的文本，例如：

```text
晨星物流济南冷链项目必须将冷链温度保持在 2 到 8 摄氏度，生产发布前还要完成安全评审。
```

选择“关键事实”，填写当前 Task ID，点击“同步生成结构化记忆”。

**口播：**

> 页面顶部的五张流程卡对应关键信息抽取、结构化记忆生成、相似记忆召回、冲突识别与融合、有效记忆入库。它们是对后端流水线的可视化说明。同步请求完成后，右侧展示后端真实返回的生成记忆数、新增、融合、更新、丢弃、冲突，以及逐条处理明细。
>
> 这里的 action、memory ID、类型、重要性、置信度和后端说明都直接来自响应。前端只负责映射标签和展示，不根据文本自行判断“这是冲突”或“应该融合”。

#### 5.2 去重、融合和聚焦入口

**操作：** 在同一场景下再次提交相同或相似文本，观察处理动作；再依次点击“冲突检测”“冲突记忆去重”“相似记忆去重”“记忆融合管理”“低价值内容过滤”等入口，观察标题、默认抽取类型和结果聚焦开关变化。

**口播：**

> 这九个入口不是九套重复页面，而是一个共享生成工作台的九种场景预设：偏好、事实、任务状态、决策、冲突、冲突去重、相似去重、融合和低价值过滤。预设会改变默认抽取类型或明细聚焦条件，但最终动作仍以本次后端响应为准。

**重要答辩口径：**

> 如果后端返回新增，我就展示新增；如果返回融合、更新、丢弃或冲突，我就展示对应动作。即使某个场景没有命中聚焦结果，页面也会明确显示空结果，不会为了让演示好看而补造一条冲突或融合记录。

#### 5.3 批量同步

**操作：** 切换为“批量同步”，每行输入一条，例如：

```text
团队前端统一使用 React 和 TypeScript。
高峰时段优先保证配送时效，普通时段优先降低运输成本。
冷链订单温度保持在 2 到 8 摄氏度。
```

点击“批量生成记忆”。

**口播：**

> 批量模式按行解析文本，一次最多 50 条。页面同时展示总体的记忆数、新增、融合和丢弃数量，以及每条输入对应的处理结果。批量响应没有单独的更新和冲突总数字段，因此前端按每条结果汇总 updated_count 和 conflict_count，避免统计漏项。

#### 5.4 单条异步和页面恢复

**操作：** 切换为“单条异步”，提交一条文本，展示 Request ID、pending/processing 状态和总体进度。若任务已经很快完成，则展示 completed 结果即可。

**口播：**

> 异步模式先提交任务，拿到 request_id 后按后端状态接口轮询。排队状态从 1 秒开始查询，处理中使用约 2 秒间隔；completed、failed 或 not_found 时停止轮询。页面会把任务上下文保存到当前浏览器会话，刷新后可以在有效期内恢复查询。这里展示的是后端提供的总体 progress，不把同一个进度伪装成五个阶段的独立进度；当前接口也没有取消任务能力，所以页面不提供取消按钮。

### 6. 多层记忆管理：约 2 分钟

**操作：** 进入“多层记忆管理”，先点击刷新。

**讲解顺序：**

1. 查看用户级、会话级、任务级和智能体级四张统计卡。
2. 使用关键字检索，例如“React”“冷链”或“2 到 8 摄氏度”。
3. 选择记忆类型，打开或关闭“二次排序”，查看检索结果。
4. 点击一条记忆的编辑按钮，修改摘要、状态、重要性、置信度或标签并保存。
5. 点击“清除记忆”，选择一条或多条记录，经过确认后清除所选记录。
6. 进入用户级、会话级、任务级三个子入口，展示不同范围说明；任务级入口输入当前 Task ID。

**口播：**

> 记忆管理页展示的是统一记忆单元：内容、类型、状态、场景、任务、更新时间等。用户级、会话级和任务级入口复用同一个管理组件，通过当前路径切换范围和说明。列表和检索分别调用真实的 memory list/search 接口，编辑调用 update 接口，删除操作有二次确认。
>
> 四层统计只有在后端统计接口返回时才显示真实条数和比例。如果统计接口不可用，页面显示“统计暂不可用”，列表仍可以独立使用；前端不会用当前页 20 条数据推算全库比例。

### 7. 多信号融合检索：约 2 分钟

**操作：** 进入“多信号融合记忆检索”或“融合排序”，填写：

- 检索内容：`济南冷链路线优化任务目前进展和下一步是什么？`
- Scene ID：当前演示场景
- Session ID：如有会话范围可填写；当前检索页面不展示 Task ID 输入框
- 返回数量：Top 5
- 二次排序：打开

点击“检索”。

**屏幕上展示：** 返回结果数、候选记忆数、检索耗时、当前策略、记忆内容、类型、场景、相关度和创建时间。

**口播：**

> 检索请求由查询、User ID、Scene ID、Session ID、记忆类型、状态、Top-K 和 rerank 参数组成。当前页面不展示 Task ID 输入框；如果要验证任务范围，可以在记忆管理或上下文页面使用 Task ID。页面把返回结果、候选数和耗时直接展示出来，相关度没有返回时显示短横线，而不是显示 0%。
>
> 左侧的语义向量、关键词、元数据、融合排序和 Top-K 是五个使用视角。当前前端接口契约没有提供 retrieval_mode 和 applied_signals 字段，因此我不会把不同标题说成已经被前端证明的五种独立算法；真正采用的检索信号和排序仍以后端实现及返回字段为准。融合入口默认打开 rerank，Top-K 入口突出返回数量控制。

### 8. 记忆上下文返回：约 2 分钟

**操作：** 进入“记忆上下文返回”，输入：

```text
请为济南冷链路线优化任务返回用户偏好、关键事实、历史决策和当前未完成事项。
```

设置最大 Token 数、候选记忆数量、单条最大字符数、记忆类型和 active 状态，填写当前 Task ID，点击“生成上下文”。

先查看“JSON 返回”，再切换“文本片段”。

**口播：**

> 上下文接口把检索结果按当前任务和长度约束组织成可调用的上下文。JSON 视图保留接口返回的结构化结果，包括 formatted_text、memory_count、estimated_tokens 和 fragments；文本视图展示可以直接注入外部智能体的 formatted_text，并支持复制。这个页面仍然是上下文生成和预览，不提供实时聊天。

### 9. 接口监控和收尾：约 1 分钟

**操作：** 依次进入“接口健康检查”“调用状态监控”“联调记录”。在调用状态监控中按 `/api/v1/memory/search` 筛选；在联调记录中查看最近检索请求和失败调用。

**口播：**

> 这里验证的是前面操作是否留下了可追踪的运行记录。健康页面主动检查后端服务、应用名、版本和本次耗时；调用状态页面读取真实 API 日志，展示请求路径、方法、响应码、错误码、耗时和时间；联调记录页面展示检索日志和最近失败调用。如果当前凭据没有管理员权限，页面会显示权限空态，而不是伪造日志。
>
> 到这里，刚才的 User、Scene、Agent 和 Task 已经贯穿接入、写入、生成、管理、检索、上下文和监控，完成了前端系统的主闭环。我负责的前端工作也主要体现在这条链路的可操作性、接口适配、状态反馈和结果可解释性上。

## 七、不要在演示中主动承诺的内容

这些内容在当前前端版本中没有足够证据，最好不要主动说成已经完成：

- 实时 AI 对话、聊天窗口或前端直接生成答案。
- 五个检索子入口已经分别证明使用五种独立算法。当前它们是同一检索工作台的不同预设，后端没有在当前契约中返回完整信号解释。
- 前端实现了向量召回、LLM 抽取或去重算法。前端只提交参数并展示后端结果。
- 可以在前端取消异步生成任务。当前接口没有取消能力。
- 前端提供 CPU、内存、磁盘、数据库连接池等基础设施监控。当前监控页面只覆盖健康、API 日志和检索日志。
- 统计接口永远有数据。没有返回时页面会显示空态。
- 导入校验等同于后端最终校验。它只是浏览器侧预校验。
- 当前版本已经完成冲突人工决策、融合预览或过滤规则管理。这些需要后端独立管理接口。
- 单条删除或全量清理在任何部署环境都无条件成功。演示前应先验证后端删除接口和当前用户权限。

## 八、模拟答辩：导师可能提出的问题与参考答案

### A. 系统定位与功能设计

#### 1. 你们的系统和普通聊天系统有什么区别？

**参考答案：**

普通聊天系统关注一次会话中的问答；本系统关注记忆资产的生命周期：数据接入、校验、结构化生成、去重融合、分层管理、检索和上下文返回。它可以为外部智能体提供记忆服务，但当前前端不包含实时聊天窗口，演示重点是记忆控制台。

#### 2. 为什么要区分 User、Scene、Agent、Session 和 Task？

**参考答案：**

它们承担不同的隔离和追踪维度：User 表示记忆归属用户，Scene 表示业务场景，Agent 表示来源或调用方，Session 表示一次会话，Task 表示长周期任务。前端在写入、生成、检索和上下文请求中携带这些标识，使数据可以按业务范围查询；真正的权限校验仍由后端完成。

#### 3. 系统文档功能很多，前端是否真的全部实现了？

**参考答案：**

我把功能分成“可操作链路”和“说明性底层能力”。当前前端保留并实现了七组入口：接入和写入、四层记忆管理、生成与去重、五类检索、四类上下文、健康与日志监控、系统设置。生成、检索和上下文的多个子入口通过共享工作台预设实现。像底层记忆模型定义、人工冲突决策、向量索引维护等没有独立后端操作接口的内容，不伪装成前端可配置页面，而是通过真实结果或空态表达。

#### 4. 为什么多个子菜单进入的是同一个页面？是不是功能没有做完？

**参考答案：**

不是简单复制页面，而是把相同的请求和响应结构抽成共享工作台，再用路由参数设置默认抽取类型、检索条件、Top-K、rerank 或结果聚焦。这样可以避免九套生成页面、五套检索页面和四套上下文页面产生行为不一致。对于真正需要独立接口的能力，仍然会单独建页面或等待后端契约确认。

### B. 前端架构与工程实现

#### 5. 为什么选择 React、TypeScript、Ant Design 和 Zustand？

**参考答案：**

React 适合将控制台拆分为页面、布局和业务组件；TypeScript 可以约束接口请求和响应字段；Ant Design 提供表单、表格、上传、弹窗和状态组件，适合管理后台；Zustand 只保存跨页面必要的配置、当前记忆和任务标识，复杂度比引入更重的状态框架低。Vite 负责开发和生产构建，React Router 负责页面级路由。

#### 6. 前端如何统一调用后端接口？

**参考答案：**

前端使用统一 Axios 实例。请求拦截器从本地配置读取 Base URL 和 API Key，设置 `X-API-Key`；业务页面不直接拼 Axios 请求，而是调用 `src/api/modules` 中的模块函数。统一请求函数检查 `{ code, message, data }` 响应包装，业务 `code` 非 0 时转换为统一错误，页面再按 loading、error、empty、success 状态反馈。

#### 7. 为什么不在每个页面中直接使用 localStorage？

**参考答案：**

为了避免配置散落，我把浏览器持久化集中在 storage 工具和 Zustand Store 中。页面只读写 Store，Store 负责规范化和保存配置。当前版本的 API Key 仍是演示和联调便利下的浏览器本地保存，生产环境需要 HTTPS、短期凭据、管理员认证或 BFF/服务端会话，并且不能把密钥写入日志和 URL。

#### 8. 前端如何处理接口统一错误？

**参考答案：**

请求层先检查 HTTP 响应和业务 `code`；如果业务失败，会把 message、error_code、trace_id 保留下来。页面根据场景展示错误提示、重试按钮、权限空态或“结果未知”提示。对于写入和生成，超时后不自动重试，因为自动重试可能造成重复记忆；应该先到列表或任务状态页确认。

#### 9. 为什么总览使用 `Promise.allSettled`？

**参考答案：**

首页的统计、Dashboard、API 日志互相独立，一个接口失败不应阻断其他面板。`Promise.allSettled` 可以分别保存成功结果和错误状态，页面展示已成功返回的数据，同时告诉用户哪些区域暂不可用，比任意一个请求失败就整页报错更适合监控型控制台。

### C. 数据写入与校验

#### 10. JSON/CSV 导入的校验是在前端还是后端？

**参考答案：**

上传后先由浏览器完成文件类型、JSON 结构、CSV 表头、content 字段和 role 的快速校验，并给出标准化预览。正式写入时仍调用后端 `/api/v1/memory/write`，后端是最终校验和持久化边界。前端校验的目标是提前发现明显错误，并不是替代后端校验。

#### 11. 为什么导入采用顺序写入，而不是一次性并发请求？

**参考答案：**

记忆写入可能触发生成、向量处理和存储，盲目并发会增加后端压力，也会让部分成功和失败难以解释。当前前端按记录顺序写入，并在完成时统计成功数和生成结果数；如果中途失败，页面标记部分完成，便于用户确认后续记录。

#### 12. 三种导入模式的区别是什么？

**参考答案：**

对话模式把内容映射成 messages；历史会话模式使用会话摘要、时间和来源；任务过程模式使用任务目标、进展和结果。它们共享文件解析和上传交互，但通过 `interaction_type` 及对应字段构造不同的后端请求，最终都进入记忆写入链路。

### D. 生成、去重与异步任务

#### 13. 前端是否实现了大模型记忆抽取和去重算法？

**参考答案：**

没有。前端提供文本、User/Scene/Task/Session 和抽取类型，调用生成接口；后端负责抽取、结构化、相似召回、冲突判断和入库。前端展示后端返回的 new、merge、update、discard、conflict、memory_id 和 details，并对动作做中文标签映射。

#### 14. 你如何证明去重融合有效？

**参考答案：**

前端验证的是请求链路和响应可解释性：相同用户、场景、任务下重复提交同一或相似文本，页面能展示后端返回的 action 和统计。需要强调的是，去重正确性属于后端算法和存储一致性验收，前端不能单独证明。联调中曾发现相同文本在部分测试中仍返回 `keep_new`，以及生成返回 ID 与列表可见数据不一致，这些已经形成后端问题清单；现场如果再次出现，我会按真实结果展示，并说明这是后端链路需要继续修复的现象，而不是前端擅自改结果。

#### 15. 为什么生成页要提供九个入口？

**参考答案：**

九个入口对应系统文档中的偏好提取、事实提取、任务状态、决策、冲突、冲突去重、相似去重、融合和低价值过滤。它们的输入输出契约相同，所以前端用一个共享工作台承载，通过 URL 预设默认抽取类型或结果筛选。这样既覆盖功能入口，又避免重复实现。

#### 16. 批量生成如何限制和统计？

**参考答案：**

批量文本按行拆分，前端限制一次最多 50 条。返回后使用后端总体的 total_memories、total_new、total_merged、total_discarded；更新和冲突总数则由每条结果中的 updated_count、conflict_count 汇总。批量处理中只展示页面级 loading，不把一个总体进度伪装成逐条进度。

#### 17. 异步生成如何避免刷新页面后丢失任务？

**参考答案：**

提交成功后保存 request_id、原始文本、User/Scene/Agent/Task/Session 和抽取类型到当前浏览器的 sessionStorage。重新打开页面时先校验快照版本和 30 分钟有效期，再继续调用状态接口。完成、失败或 not_found 后停止轮询并清理快照；轮询失败不会自动重新提交生成请求。

#### 18. 为什么没有取消异步任务的按钮？

**参考答案：**

当前后端异步接口只提供提交和状态查询，没有取消接口。前端不能做一个看起来能取消、实际不能撤销后端任务的按钮，所以只提供状态查看、终态关闭和失败后重新查询。后续后端提供取消契约后，再补充取消状态和权限控制。

### E. 记忆管理、检索和上下文

#### 19. 用户级、会话级、任务级和智能体级是如何区分的？

**参考答案：**

前端展示的是后端返回的层级统计和列表字段。User/Session/Task/Agent 标识是关联维度，不应简单把“有 agent_id”当成智能体级记忆。四层统计需要后端按照统一的 memory_scope 口径聚合；后端未提供统计时，前端显示不可用，不用分页数据推导。

#### 20. 五个检索页面是否真的使用了五种算法？

**参考答案：**

当前版本只能说它们是五种检索使用视角。五个入口共享 `/api/v1/memory/search`，语义和关键词页面主要改变输入提示和界面说明，元数据页突出类型/状态/范围，融合页默认开启 rerank，Top-K 页突出数量控制。当前响应没有完整的 `retrieval_mode`、`applied_signals` 或 `score_breakdown`，所以我不会把页面标题当成算法证明；算法执行和信号解释以后端契约为准。

#### 21. 相关度没有返回时为什么不显示 0？

**参考答案：**

0 表示算法明确计算出零分，缺失或 null 表示服务没有返回评分，两者语义不同。前端把缺失值显示为短横线或“未返回评分”，避免把“没有数据”误报成“相关度为零”。

#### 22. 上下文页和聊天页有什么关系？

**参考答案：**

上下文页是为外部智能体准备输入的工作台，不负责生成最终回答。它调用 context 接口，按查询、类型、状态、Task ID、Top-K、Token 预算和单条长度组织记忆，输出 JSON 或 formatted_text。外部智能体拿到文本片段后，才可以在自己的对话链路中使用。

#### 23. 为什么 `fragments` 数量不一定等于 `memory_count`？

**参考答案：**

memory_count 是后端定义的引用记忆统计，fragments 是具体返回的结构片段，两者可能因为分组、合并、压缩或响应契约而不完全相等。前端直接展示后端给出的统计，不根据数组长度覆盖它。

### F. 任务、监控和数据真实性

#### 24. 任务页为什么没有完整的任务列表？

**参考答案：**

当前后端交付给前端的任务能力是创建任务、更新任务进度和按 Task ID 查询进度，因此页面形成的是“创建—查询—更新—再查询”的闭环。任务列表、详情、完成、取消等接口如果没有稳定契约，前端不自行模拟；后续可以在后端提供接口后扩展。

#### 25. 监控页监控了哪些内容？为什么没有 CPU 和内存？

**参考答案：**

当前前端监控的是可由后端接口证明的内容：健康状态、应用版本、本次健康检查耗时、API 调用日志、检索日志和最近失败调用。CPU、内存、磁盘和数据库连接池属于基础设施监控，需要 Prometheus、云监控或专门运维接口，不应在没有数据源时写死在前端。

#### 26. 首页的数字是否是 Mock 数据？

**参考答案：**

当前首页优先使用 admin stats、Dashboard 聚合和 API 日志的真实字段；接口未返回时显示 0、暂无统计或空态。前端没有用固定成功率、固定告警或当前分页样本冒充全局统计。演示时如果某一张卡为空，我会把它解释为当前接口数据状态，而不是补一个好看的数字。

#### 27. 如果后端返回 HTTP 200，但业务 code 是失败怎么办？

**参考答案：**

统一响应解析会继续检查业务 `code`，只要 code 非 0 就转换为错误，并保留 message、error_code 和 trace_id。这样不会把 HTTP 200 下的业务失败误显示成成功。监控日志也需要后端同时记录 HTTP 状态和业务错误码，避免两套口径不一致。

#### 28. 当前前端做了哪些测试？

**参考答案：**

当前工作区执行 `pnpm check` 已通过：lint 通过，9 个测试文件、37 项测试通过，TypeScript 项目构建和 Vite 生产构建通过。测试覆盖导入解析、接口响应解包、配置、任务、生成预设和异步任务恢复等逻辑。接口算法效果、去重正确性和存储一致性仍需要后端集成测试和真实数据验收，不能用前端构建通过替代。

#### 29. 如果用户输入了别人的 User ID，前端能阻止吗？

**参考答案：**

前端可以要求 User ID 非空并在请求中携带它，但不能把前端输入当作安全边界。真正的用户授权、Agent 权限、Scene 隔离和管理员日志权限必须由后端认证和授权完成。前端对 401/403 提供明确反馈，生产环境还要使用 HTTPS 和安全的凭据管理。

#### 30. 这个系统后续最值得改进什么？

**参考答案：**

优先级有四项：第一，后端完善去重、偏好抽取和生成结果与列表/检索的一致性；第二，为检索返回 retrieval_mode、applied_signals 和 score_breakdown；第三，补齐任务列表、详情、完成和取消等管理接口；第四，生产环境启用 HTTPS、管理员认证和更安全的密钥托管。前端方面可以继续增加浏览器端 E2E 演示链路、结果导出和更细的可观测性。

### G. 可能的尖锐追问

#### 31. 你是不是把页面标题换了，就当成功实现了功能？

**参考答案：**

不是。页面标题和预设只是导航层，是否完成以真实请求、响应字段和可追踪状态为准。生成页会展示实际 action 和 memory_id，检索页展示实际结果数和耗时，上下文页展示原始返回结构；没有后端字段的能力会显示空态或明确说明，而不是根据标题补数据。

#### 32. 如果演示时去重结果不理想，你怎么解释？

**参考答案：**

我会先区分前端链路和后端算法。前端检查请求中的 User、Scene、Task、抽取类型和文本是否正确，并完整显示后端 action、计数和说明。如果请求正确但后端仍返回重复新增，这说明去重召回、存储一致性或规则阈值需要后端修复。我不会在前端把新增改成融合，因为那会掩盖真实问题。

#### 33. 为什么首页有些模块是空的？

**参考答案：**

控制台首先保证数据真实性。Dashboard 缺少 `latest_context`、趋势或告警状态时，前端按空态处理；这比显示固定演示数据更可信。具体业务操作仍可从写入、生成、检索和上下文页面执行，数据产生后再刷新首页。

#### 34. 顶部搜索、通知、帮助和退出登录能演示吗？

**参考答案：**

它们属于控制台壳层布局入口，不是本次前端业务闭环的重点。当前业务检索通过记忆管理和检索工作台完成；如果现场被问到，我会明确说顶部控件当前不作为已验收的核心功能，不现场点击制造假交互。

## 九、最后的答辩原则

1. 不把后端算法说成前端算法。
2. 不把路径预设说成独立接口或独立算法。
3. 不把空态说成系统没有功能，而要说明“当前接口没有返回数据”。
4. 不把 HTTP 200 直接说成业务成功，要看统一响应中的业务 code。
5. 不在超时后立即重复写入或生成，先用列表、任务状态或日志确认。
6. 遇到真实缺陷时，用“前端已定位、后端待闭环、页面不伪造结果”的口径回答。
