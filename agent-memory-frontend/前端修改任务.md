## 前置条件（前端先看这里，正文未覆盖）

> 指导者补充：以下身份/鉴权前提会影响 #1/#2/#9/#13/#14 多个任务，务必先了解，否则改完仍可能联调不通。

- **身份来自 Header，不是 body**：后端从请求头识别身份。前端 `src/api/client.ts` 的请求拦截器已自动给每个请求带三个 Header：
  - `X-API-Key`（智能体密钥，来自「凭据管理」页保存的 apiKey）
  - `X-User-Id`（用户 ID）
  - `X-Agent-Id`（智能体 ID）
  因此 #7 第 3 条删 `MemoryWritePayload.agent_id` 是对的（后端从 header 取，不读 body）。同理 #9 的 `memory_scope=agent` 依赖 `X-Agent-Id`，#14 的画像按 user_id 查依赖 `X-User-Id`。
- **鉴权开关 AUTH_ENABLED**：后端 `config/settings.yaml` 里 `AUTH_ENABLED` 默认 `false`（开发阶段跳过鉴权），上线置 `true` 后强制校验 `X-API-Key` 或 `Authorization: Bearer <token>`。本地联调通常无需改，但**上线前必须确认 apiKey 已保存**，否则生产环境所有请求会 401。
- **登录改造后 header 来源会变**：#13 完成后，`X-User-Id` 由登录返回的 `user_id` 自动注入（见 #13 第 2 条），不再手动配置。

## 一、紧急：功能不可用（先改这几个）

### 1. `/memory/list` 方法用错（导致 405）

- **问题**：前端用 `GET`，后端是 `POST`，导致列表请求 405，多层记忆管理四个层级列表全加载失败
- **现状**：`src/api/modules/memory.ts:102` 的 `listMemories` 用 `method: 'GET'`
- **改法**：`method` 改为 `'POST'`（参数保留 query string 或改用 `params`，后端是 Query 参数，两种都行）
- **后端**：`POST /api/v1/memory/list`（已就绪，无需后端改动）

### 2. `/memory/write` 响应结构过时（导致导入界面崩溃）

- **问题**：后端 write 已改为「只落 L0、异步抽取」，返回 `{accepted, session_id, l0_count, record_ids}`，但前端还按旧的 `{mode, results[]}` 处理，导致 `result.results` 为 undefined，`.filter` 抛错
- **现状**：
  - `src/api/types.ts:297` `MemoryWriteResult = { mode, results[] }`（旧）
  - `src/pages/Ingestion/index.tsx:150-153` `result.results.filter(...)`（会崩溃）
- **改法**：
  1. `types.ts` 的 `MemoryWriteResult` 改为 `{ accepted: boolean; session_id: string; l0_count: number; record_ids: string[] }`
  2. `Ingestion/index.tsx` 去掉 `result.results.filter` 和「生成 N 条记忆」统计（异步抽取下无法从 write 响应即时得知记忆数），改为显示「已提交 N 条记录」；注意 `generatedCount` 还贯穿 `IngestionHistoryItem.resultCount` → 表格「处理结果数」列（`index.tsx:353`），要一并改为按 `l0_count`/`record_ids.length` 计数（即「已提交记录数」）
- **后端**：`POST /api/v1/memory/write` 返回 `{accepted, session_id, l0_count, record_ids}`

### 3. `/memory/write` 超时与注释过时

- **问题**：注释写「耗时 5-15 秒」+ `timeout: 60000`，但后端已改成毫秒级返回
- **现状**：`src/api/modules/memory.ts:40`（注释）+ `timeout: 60000`
- **改法**：注释改「毫秒级返回」，`timeout: 60000` 去掉（用默认超时）
- **后端**：无需改动

### 4. `/memory/delete` 的 500 降级 workaround（已确认：后端无 500，删 workaround）

- **问题**：前端 `deleteMemory` 捕获 500 后降级调 `/memory/update` 置 `status=deleted`，注释称「deployed 单删端点返回 500」
- **现状**：`src/api/modules/memory.ts:155-183`
- **已确认（2026-08-19 后端实测）**：`DELETE /memory/delete` 返回 200，后端**无 500 bug**
- **改法**：删掉这个 workaround，`deleteMemory` 直接调 `DELETE /memory/delete`（去掉 try/catch 降级调 update 的逻辑）
- **后端**：`DELETE /api/v1/memory/delete`（正常，无需后端改动）

## 接口契约参考（改前端必看）

> 每个接口的完整请求/响应参数 + 示例。响应统一 `{code, message, data}` 包装，下表只列 `data` 内字段。身份走 Header（见「前置条件」）。

### 1. 记忆列表（#1）`POST /api/v1/memory/list`

**请求（Query 参数）**：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| user_id | string | ✅ | 用户标识 |
| scene_id | string | ❌ | 场景过滤 |
| task_id | string | ❌ | 任务过滤 |
| session_id | string | ❌ | 会话过滤 |
| memory_scope | string | ❌ | 层级过滤：user/session/task/agent |
| page | int | ❌ | 页码，默认 1 |
| page_size | int | ❌ | 每页条数，默认 20，1-100 |

**响应 data**：

```json
{"items": [{"memory_id":"...","content":"...","memory_type":"fact","memory_scope":"user",...}], "total": 15, "page": 1, "page_size": 20}
```

### 2. 记忆写入（#2 #3）`POST /api/v1/memory/write`

**请求（body）**：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| user_id | string | ✅ | 用户标识 |
| session_id | string | ✅ | 会话标识 |
| scene_id | string | ❌ | 场景标识 |
| task_id | string | ❌ | 任务标识 |
| interaction_type | string | ❌ | dialogue / session / task_process，默认 dialogue |
| messages | array | dialogue 必填 | `[{role, content}]`，role ∈ user/assistant/system/tool/agent |
| session_summary | string | ❌ | session 类型的摘要 |
| task_goal / task_progress / task_result | string | ❌ | task_process 类型 |

**响应 data**：


> 注意：write 只落 L0，**异步**抽取 L1，响应不含记忆明细。
