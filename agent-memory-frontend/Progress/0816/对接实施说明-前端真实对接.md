## 二、修改内容

### 1. 请求层 — 鉴权 Header 对齐（关键）

[src/api/client.ts](../../src/api/client.ts) 请求拦截器由「只设置 `X-API-Key`」改为统一维护三个 Header：

| Header | 来源 |
|---|---|
| `X-API-Key` | 本地配置 `apiKey` |
| `X-User-Id` | 本地配置 `userId` |
| `X-Agent-Id` | 本地配置 `agentId` |

存在即设置、为空即移除，严格对齐文档「第 3 步起每个请求携带三 Header」的约定。

### 2. 类型层 — 新增与修正

[src/api/types.ts](../../src/api/types.ts)：

- 新增 `SessionCreatePayload / SessionInfo / SessionListResult / SessionUpdatePayload / SessionCloseResult`

- `AppConfig` 增加 `sessionId`（持久化活动会话，写记忆闭环用）
- 修正枚举对齐后端：`TaskStatus` 补 `'cancelled'`；`MemoryWriteItem.event` 补 `'UPDATE'`；`MemoryWriteResult` 补 `mode`

### 3. API 模块 — 新增/补齐

- 新增 [src/api/modules/session.ts](../../src/api/modules/session.ts)：`createSession`（`POST /api/v1/session`）、`getSession`、`listSessions`、`updateSession`、`closeSession`（`POST /api/v1/session/{id}/close`）

- [src/api/modules/agent.ts](../../src/api/modules/agent.ts)：新增 `getAgent / listAgents / updateAgent / disableAgent`
- [src/api/modules/memory.ts](../../src/api/modules/memory.ts)：`listMemories` 由 POST 改 **GET**（对齐文档）；`writeMemories` 超时单独放宽到 **60s**（写入链路 5-15s）

## 四、已知风险与后续建议

1. **跨域 CORS**：开发服务器直连远程 IP，若后端未开 CORS 会被浏览器拦截。兜底方案：在 `vite.config.ts` 增加 `server.proxy['/api'] → http://120.27.207.238:8000`，请求路径改相对 `/api`。
2. **鉴权失效**：`api_key` 仅注册/轮换时返回一次，若被覆盖或轮换，旧 Key 全部请求 401。页面当前对 401 会走通用报错提示，建议后续增加「401 → 引导重新注册/轮换」的专门处理。
3. **枚举收敛**：后端 `memory_type` 为 `fact/preference/task_state/process/correction`，而检索/上下文页面的下拉仍含 `decision/constraint` 等非枚举值，可能导致 422 或空结果，建议下一步在页面层收敛选项。
4. **`status` 取值**：后端为 `active/deleted/expired`，记忆编辑表单仍含 `archived` 选项，需在真实后端上验证。
5. **`listMemories` GET/POST**：已按文档改为 GET；若远程返回 405，需回退 POST（已隔离为单一函数，改动可控）。
6. **`/health` 路径**：监控页 `getHealth` 请求 `/api/v1/health`，使用说明写 `/health`，需实测确认，暂不属主链路范围。
7. **`deleteMemory` 的 500 降级 hack**（[memory.ts](../../src/api/modules/memory.ts)）为历史遗留，与文档定义的 delete 行为可能冲突，本次未改动，建议后续按文档清理。

## 五、前端运行方式

### 前置要求

- Node.js ≥ 20；pnpm 已安装（项目锁定 `pnpm 11.7.0`）
- 依赖已安装：在项目根目录执行 `pnpm install`
- 首次访问需先完成配置：Base URL 已默认指向 `http://120.27.207.238:8000`（`.env.*`），还需在对应页面配置 `User ID / Agent ID / Scene ID`（后续主链路请求会通过 `X-API-Key / X-User-Id / X-Agent-Id` 三个 Header 自动携带）

### 启动开发服务器

```bash
pnpm dev
```

启动后按终端提示的本地地址（默认 `http://localhost:5173`）在浏览器打开即可。

### Windows PowerShell 无法运行 pnpm 的解决办法

**现象**：在 PowerShell 中执行 `pnpm dev` 报错：

```
pnpm : 无法加载文件 C:\Users\92986\AppData\Roaming\npm\pnpm.ps1，因为在此系统上禁止运行脚本
```

**原因**：pnpm 的启动器是 `pnpm.ps1`（一个 PowerShell 脚本），而系统执行策略默认 `Restricted`，禁止运行任何 `.ps1` 脚本。

**解决方式一（立即生效，不改系统设置）**：改用 `.cmd` 版本，不经过脚本执行策略：

```bash
pnpm.cmd dev
```

**解决方式二（一劳永逸，推荐）**：放行本地脚本（只需当前用户，无需管理员）：

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

然后关闭并重新打开终端，再执行 `pnpm dev`。`RemoteSigned` 只放行本地创建的脚本（npm/pnpm 启动器即此类），下载的脚本仍需数字签名，不会降低实际安全性。

### 其他常用命令

```bash
pnpm build    # 生产构建（对应上文验证结果中的 vite build）
pnpm test     # 运行 vitest 测试
pnpm lint     # oxlint 代码检查
```
