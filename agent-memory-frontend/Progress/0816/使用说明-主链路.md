# 智能体记忆系统 — 使用说明（主链路时序）

> 从「创建场景」到「数据落库」的完整调用时序，模拟一个真实用户接入的全过程。

## 服务器网址

| 项 | 地址 |
|---|---|
| **API 根地址** | `http://120.27.207.238:8000` |
| **Swagger 文档** | `http://120.27.207.238:8000/docs` |
| **健康检查** | `http://120.27.207.238:8000/health` |

---

## 0. 统一约定（先读这里）

**统一响应包裹**：所有接口返回 `{code, message, data}`

| 字段 | 含义 |
|---|---|
| `code` | `0`=成功；`-1`=业务错误；`-2`=处理失败 |
| `message` | 状态描述（如 "ok"、"创建成功"） |
| `data` | 业务数据（成功时才有，结构因接口而异） |

**鉴权 Header**（第 2 步拿到 api_key 后，后续所有接口都要带）：

| Header | 含义 |
|---|---|
| `X-API-Key` | 智能体 API Key（注册智能体时返回的 `api_key`） |
| `X-User-Id` | 用户唯一标识（业务侧用户 ID） |
| `X-Agent-Id` | 智能体 ID |

---

## 第 1 步：创建场景

**① 做什么、为什么**：场景（Scene）是租户隔离的第二维度（Agent → Scene → Data）。所有记忆、会话、任务都挂在某个场景下，用于把不同业务线/项目的数据隔离开。

**② 入参**：`POST /api/v1/scene`

```json
{
  "scene_name": "客服场景",       // 必填，1-256 字符
  "description": "处理咨询与退款", // 可选，场景描述
  "extra_meta": {}                 // 可选，扩展元数据
}
```

| 入参 | 说明 |
|---|---|
| `scene_name` | 场景名称，必填，长度 1-256 |
| `description` | 场景描述，可选 |
| `extra_meta` | 扩展字段（自定义 KV），可选 |

**③ 响应**：

```json
{
  "code": 0, "message": "创建成功",
  "data": {
    "scene_id": "scene_2aafc553",
    "scene_name": "客服场景",
    "description": "处理咨询与退款",
    "is_active": true,
    "created_at": "2026-08-13T15:09:45Z"
  }
}
```

| 响应字段 | 含义 |
|---|---|
| `scene_id` | 场景唯一标识（服务端生成，后续要用） |
| `scene_name` | 场景名称 |
| `is_active` | 是否启用 |
| `created_at` | 创建时间 |

**④ 下一步**：拿 `scene_id` 去注册智能体。

**⑤ 边界条件**：

- `scene_name` 必填，空串或超 256 字符会被拒绝。
- `scene_id` 由服务端自动生成（`scene_` 前缀），无需也不能客户端指定。
- 场景是「软删除」（停用 `is_active=false`），不会物理删除。

---

## 第 2 步：注册智能体（拿 API Key）

**① 做什么、为什么**：智能体（Agent）是调用方身份。注册后拿到 `api_key`，后续所有写/读接口都用它鉴权。数据库只存 key 的 SHA256 哈希，**明文 key 只返回这一次**。

**② 入参**：`POST /api/v1/agent/register`

```json
{
  "agent_name": "客服助手",                    // 必填
  "scene_id": "scene_2aafc553",                // 必填，上一步拿到的场景
  "permissions": ["read", "write"]             // 可选，默认 ["read","write"]
}
```

| 入参 | 说明 |
|---|---|
| `agent_name` | 智能体名称，必填 |
| `scene_id` | 所属场景，必填，用于数据隔离（**必须是第 1 步创建且 active 的场景**） |
| `permissions` | 权限列表，可选，默认 `["read","write"]` |

**③ 响应**：

```json
{
  "code": 0, "message": "注册成功 — API Key 仅显示一次，请妥善保存",
  "data": {
    "agent_id": "agent_2661d75215c04820",
    "agent_name": "客服助手",
    "api_key": "mem_5a244bb...",
    "api_key_prefix": "mem_5a24****",
    "scene_id": "scene_2aafc553",
    "is_active": true,
    "created_at": "2026-08-13T15:09:50Z"
  }
}
```

| 响应字段 | 含义 |
|---|---|
| `agent_id` | 智能体唯一标识（后续放 `X-Agent-Id` 头） |
| `api_key` | **明文 Key，仅此一次返回，妥善保存**（后续放 `X-API-Key` 头） |
| `api_key_prefix` | Key 前缀（展示用） |
| `scene_id` | 所属场景 |

**④ 下一步**：用 `agent_id` + `api_key` 创建任务或会话。

**⑤ 边界条件**：

- `scene_id` 必须存在且 `is_active=true`，否则报「场景不存在或已停用」。
- **`api_key` 只返回这一次**，丢失后只能通过「轮换 key」接口生成新 key（旧 key 立即失效）。
- 同一个场景可以注册多个智能体。

---

## 第 3 步：创建任务（跨会话的工作单元）

**① 做什么、为什么**：任务（Task）是一个有明确目标的工作单元（如「处理订单 DH001 退货」），可以跨多个会话。会话和记忆都能关联 `task_id`，任务用于聚合这些会话的目标、进展和已积累的记忆。

**② 入参**：`POST /api/v1/task`

```json
{
  "user_id": "user_001",                    // 必填
  "scene_id": "scene_2aafc553",             // 可选
  "title": "处理订单DH001退货",              // 可选，任务标题（≤512）
  "goal": "完成退货全流程并确认退款到账",     // 可选，任务目标
  "session_id": null,                        // 可选，关联会话
  "extra_meta": {}
}
```

请求头：`X-API-Key`、`X-Agent-Id`

| 入参 | 说明 |
|---|---|
| `user_id` | 必填，用户标识 |
| `scene_id` | 可选，所属场景 |
| `title` | 可选，任务标题 |
| `goal` | 可选，任务目标 |
| `session_id` | 可选，关联会话（也可在创建会话时反向关联） |

**③ 响应**：

```json
{
  "code": 0, "message": "创建成功",
  "data": {
    "task_id": "task_bdd985f5b79f",
    "user_id": "user_001",
    "title": "处理订单DH001退货",
    "goal": "完成退货全流程并确认退款到账",
    "status": "pending",
    "started_at": "2026-08-13T15:09:55Z"
  }
}
```

| 响应字段 | 含义 |
|---|---|
| `task_id` | 任务唯一标识（服务端生成） |
| `status` | 任务状态，初始 `pending` |
| `started_at` | 开始时间 |

**④ 下一步**：拿 `task_id` 创建会话（关联到这个任务）。

**⑤ 边界条件**：

- `task_id` 服务端生成（`task_` 前缀），客户端不能指定。
- 状态机有合法性校验：`pending → in_progress/completed/cancelled`，非法跳转会被拒绝。
- 任务是可选的——纯闲聊场景可以不建任务，直接建会话。

---

## 第 4 步：创建会话

**① 做什么、为什么**：会话（Session）是记忆的组织单元。一次对话对应一个会话，记忆会绑定 `session_id`，关闭会话时才能按会话维度做压缩汇总。

**② 入参**：`POST /api/v1/session`

```json
{
  "user_id": "user_001",                    // 必填，业务侧用户 ID
  "agent_id": "agent_2661d75215c04820",     // 可选，不传则取 Header 里的 X-Agent-Id
  "scene_id": "scene_2aafc553",             // 可选
  "task_id": "task_bdd985f5b79f",           // 可选，关联到第 3 步的任务
  "extra_meta": {}
}
```

请求头：`X-API-Key`、`X-Agent-Id`

| 入参 | 说明 |
|---|---|
| `user_id` | 必填，用户唯一标识（会被 `strip+lower` 归一化） |
| `task_id` | 可选，关联任务（把会话挂到任务下） |
| `agent_id` / `scene_id` | 可选，缺省时从 Header / 空值兜底 |

**③ 响应**：

```json
{
  "code": 0, "message": "创建成功",
  "data": {
    "session_id": "sess_6592b530cb2e",
    "user_id": "user_001",
    "agent_id": "agent_2661d75215c04820",
    "scene_id": "scene_2aafc553",
    "task_id": "task_bdd985f5b79f",
    "status": "active",
    "started_at": "2026-08-13T15:10:00Z"
  }
}
```

| 响应字段 | 含义 |
|---|---|
| `session_id` | 会话唯一标识（服务端生成，下一步写记忆必填） |
| `status` | 会话状态（active / closed） |
| `started_at` | 开始时间 |

**④ 下一步**：用 `session_id` 写入记忆。

**⑤ 边界条件**：

- `session_id` 由服务端生成（`sess_` 前缀），客户端不能指定。
- `user_id` 会被统一转小写，所以 `User_001` 和 `user_001` 是同一个用户。

---

## 第 5 步：写入记忆（★ 数据落库）

**① 做什么、为什么**：这是核心链路。内部流程：**原始对话落库 → LLM 抽取 → 结构化生成 → 向量检索去重（ADD/MERGE/UPDATE/SKIP）→ 写记忆主表 + 向量表 + 历史表**。支持三种数据类型。

**② 入参**：`POST /api/v1/memory/write`

```json
{
  "user_id": "user_001",               // 必填
  "scene_id": "scene_2aafc553",        // 可选（有则传）
  "session_id": "sess_6592b530cb2e",   // ★ 必填
  "task_id": "task_bdd985f5b79f",      // 可选，关联任务
  "interaction_type": "dialogue",      // dialogue | session | task_process
  "messages": [                        // dialogue 类型必填
    {"role": "user", "content": "我买的衣服尺寸不合适想退货，订单号DH001"},
    {"role": "assistant", "content": "好的，帮您提交退货申请，退款3个工作日到账"}
  ]
}
```

请求头：`X-API-Key`、`X-User-Id`、`X-Agent-Id`

**三种数据类型**（通过 `interaction_type` 区分）：

| 类型 | 使用场景 | 专用字段 |
|---|---|---|
| `dialogue` | 当前实时对话 | `messages`（必填） |
| `session` | 导入历史会话 | `session_time`、`session_source`、`session_summary` |
| `task_process` | 任务过程数据（关联任务时常用） | `task_goal`、`task_progress`、`task_result` |

`task_process` 示例：

```json
{
  "user_id": "user_001",
  "session_id": "sess_6592b530cb2e",
  "task_id": "task_bdd985f5b79f",
  "interaction_type": "task_process",
  "task_goal": "完成退货全流程",
  "task_progress": "已提交退货申请，等待仓库质检",
  "task_result": "退款将在7个工作日内到账"
}
```

**③ 响应**：

```json
{
  "code": 0, "message": "ok",
  "data": {
    "mode": "pipeline",
    "results": [
      {"id": "mem_48217e6d", "memory": "用户订单DH001的退货申请已提交...", "event": "ADD"},
      {"id": "",            "memory": "...", "event": "SKIP"}
    ]
  }
}
```

| 响应字段 | 含义 |
|---|---|
| `mode` | `pipeline`(正常) / `mq`(异步) / `degraded`(降级，抽取失败时全部返回 SKIP) |
| `results[].id` | 记忆 ID（`ADD/MERGE/UPDATE` 有值，`SKIP` 为空） |
| `results[].memory` | 记忆内容摘要 |
| `results[].event` | **`ADD`**=新增 / **`MERGE`**=合并进已有记忆 / **`UPDATE`**=覆盖更新（纠正矛盾）/ **`SKIP`**=丢弃（重复/无价值） |

**④ 数据落库到哪些表**（这一步实际写入）：

| 表 | 写入内容 |
|---|---|
| `T_INTERACTION_RECORD` | 原始对话记录（每条消息一行） |
| `T_MEMORY` | 记忆主表（content、memory_type、importance、confidence、version 等） |
| `T_MEMORY_VECTOR` | 向量桥接表（memory_id ↔ Qdrant 点 ID） |
| Qdrant | 记忆向量（用于相似检索） |
| `T_MEMORY_HISTORY` | 版本历史快照（`MERGE`/`UPDATE` 时记录旧值） |
| `T_DEDUP_AUDIT` | 去重审计（action、matched_memory_id、新旧 version） |
| `T_SESSION` | 更新 `message_count` |

**④ 下一步**：每轮对话后，更新任务进展（第 6 步）。

**⑤ 边界条件**：

- `dialogue` 类型 `messages` 必须非空，否则报 422。
- `session_id` 必传（已强制），不传会报「Field required」。
- `interaction_type` 只接受 `dialogue/session/task_process`，其他值报错。
- 同一段重复内容再写一次会被判 `SKIP`（去重丢弃）。

---

## 第 6 步：更新任务进展

**① 做什么、为什么**：每轮对话后，把任务的最新进展、已完成/待办事项回写到任务上，让任务状态和实际进度保持同步，前端也能展示「该任务做到哪一步了」。

**② 入参**：`PUT /api/v1/task/{task_id}`

```json
{
  "status": "in_progress",              // 可选，pending/in_progress/completed/cancelled
  "progress": "已提交退货申请，等待仓库质检", // 可选，当前进展描述
  "completed_items": ["提交退货申请"],   // 可选，已完成事项
  "pending_items": ["仓库质检", "退款到账"] // 可选，待处理事项
}
```

| 入参 | 说明 |
|---|---|
| `status` | 任务状态（受状态机约束） |
| `progress` | 当前进展描述文本 |
| `completed_items` / `pending_items` | 已完成 / 待办事项清单 |

**③ 响应**：

```json
{
  "code": 0, "message": "更新成功",
  "data": {
    "task_id": "task_bdd985f5b79f",
    "updated": true,
    "status": "in_progress"
  }
}
```

**④ 下一步**：需要时检索记忆（第 7 步）或返回上下文（第 8 步）。

**⑤ 边界条件**：

- 状态跳转受状态机约束（如 `pending` 不能直接跳 `completed`，必须先 `in_progress`），非法跳转返回冲突错误。
- 不传的字段不会被覆盖（只更新传入的字段）。

---

## 第 7 步：检索记忆（可选，验证落库结果）

**① 做什么、为什么**：验证上一步的记忆确实写入并能被检索到。走「Qdrant 向量检索 → 桥接表 → PG 取权威数据 → 后过滤 + 时间衰减排序」链路。

**② 入参**：`POST /api/v1/memory/search`

```json
{
  "query": "退款",           // 必填，检索文本
  "user_id": "user_001",     // 必填
  "top_k": 5,                // 可选，默认 10，范围 1-50
  "memory_types": ["fact"],  // 可选，按类型过滤
  "status": ["active"]       // 可选，默认只查 active
}
```

**③ 响应**：

```json
{
  "code": 0,
  "data": {
    "query": "退款",
    "total_candidates": 4,
    "results": [
      {
        "memory_id": "mem_48217e6d",
        "content": "用户订单DH001的退货申请已提交，退款将在3个工作日内到账",
        "summary": "...",
        "memory_type": "task_state",
        "relevance_score": 0.82,
        "importance": 0.8,
        "confidence": 0.9,
        "session_id": "sess_6592b530cb2e"
      }
    ],
    "elapsed_ms": 180
  }
}
```

| 响应字段 | 含义 |
|---|---|
| `total_candidates` | 向量候选总数 |
| `results[].content` | 记忆内容 |
| `results[].relevance_score` | 综合相关度（向量 + 新近性 + 重要性 + 置信度） |
| `results[].memory_type` | 记忆类型（fact/preference/task_state/process/correction） |

**④ 下一步**：需要喂给大模型时，用「上下文」接口（第 8 步）。

**⑤ 边界条件**：`top_k` 上限 50；短查询（如「退款」两字）在阈值 0.7 下可能检索不到（当前已知问题，待修复）。

---

## 第 8 步：返回上下文（可选）

**① 做什么、为什么**：把检索到的相关记忆按类型分组，拼成一段可直接塞给 LLM 的 prompt 上下文。

**② 入参**：`POST /api/v1/memory/context`

```json
{
  "query": "退款进度",       // 必填
  "user_id": "user_001",     // 必填
  "max_tokens": 2000,        // 可选，默认 3000
  "top_k": 5,
  "group_by_type": true      // 是否按类型分组
}
```

**③ 响应**：

```json
{
  "code": 0,
  "data": {
    "formatted_text": "【用户偏好】...\n【关键事实】...\n【任务状态】...",
    "memory_count": 3,
    "estimated_tokens": 450
  }
}
```

| 响应字段 | 含义 |
|---|---|
| `formatted_text` | 拼好的上下文文本（按类型分组） |
| `memory_count` | 命中记忆数 |
| `estimated_tokens` | 估算 token 数 |

**④ 下一步**：把 `formatted_text` 拼进 LLM 对话即可；工作做完后完成任务（第 9 步）。

**⑤ 边界条件**：`max_tokens` 控制截断，记忆按相关度从高到低装配，超限截断。

---

## 第 9 步：完成任务

**① 做什么、为什么**：工作目标达成后，把任务标记为 `completed`，记录结束时间。

**② 入参**：`POST /api/v1/task/{task_id}/complete`（无 body，`task_id` 放 URL）

**③ 响应**：

```json
{
  "code": 0, "message": "任务已完成",
  "data": {
    "task_id": "task_bdd985f5b79f",
    "status": "completed",
    "ended_at": "2026-08-13T15:19:00Z"
  }
}
```

**④ 下一步**：关闭会话（第 10 步）。

**⑤ 边界条件**：任务不存在会报 404；`complete` 是直接置为 `completed`（等价于 `PUT` 传 `status=completed`）。

---

## 第 10 步：关闭会话（压缩汇总）

**① 做什么、为什么**：会话结束时，把「过程类」碎片记忆（task_state/process/correction）压缩成一条摘要，`preference/fact` 升级为长期记忆（`session_id` 置空），旧碎片标记 `expired` 并删除向量。

**② 入参**：`POST /api/v1/session/{session_id}/close`（无 body，`session_id` 放 URL）

**③ 响应**：

```json
{
  "code": 0,
  "data": {
    "session_id": "sess_6592b530cb2e",
    "status": "closed",
    "total_memory_count": 5,
    "kept_count": 2,
    "compressed_count": 3,
    "summary_text": "用户已提交订单DH002的退货申请...",
    "ended_at": "2026-08-13T15:20:00Z"
  }
}
```

| 响应字段 | 含义 |
|---|---|
| `total_memory_count` | 该会话总记忆数 |
| `kept_count` | 保留（pref/fact）数 |
| `compressed_count` | 被压缩的碎片数 |
| `summary_text` | 生成的会话摘要 |

**⑤ 边界条件**：会话不存在会报 404；关闭是幂等的（重复关闭以最后状态为准）。

---

## 完整调用顺序回顾

```
1.  POST /scene                  → scene_id
2.  POST /agent/register         → agent_id + api_key（存好！）
3.  POST /task                   → task_id（可选，有明确工作目标时）
4.  POST /session                → session_id（可关联 task_id）
5.  POST /memory/write           → 记忆落库（T_MEMORY 等 7 张表）
6.  PUT  /task/{id}              → 更新任务进展（每轮对话后）
7.  POST /memory/search          → 验证检索
8.  POST /memory/context         → 拼 LLM 上下文
9.  POST /task/{id}/complete     → 完成任务
10. POST /session/{id}/close     → 压缩汇总
```

**鉴权提醒**：第 1、2 步无需鉴权；从第 3 步开始，每个请求都要带 `X-API-Key`（= 注册返回的 api_key）+ `X-User-Id` + `X-Agent-Id` 三个 Header。
