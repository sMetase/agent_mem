> 记录日期：2026-08-13
> 对照对象：`Progress/API接口文档.md`（后端接口契约） ↔ 本项目 `src/api` 及页面实际调用
> 对照方式：逐接口核对——是否在 `src/api/modules` 封装、是否被页面调用、调用方式是否与文档一致
> 结论一句话：**文档 44 个唯一接口中，前端实际使用 21 个，封装未用 1 个，完全未用 22 个**；另有 `/health` 为前端在用但文档未收录。

| 状态 | 数量 | 说明 |

| ✅ 已封装且已使用 | 21 | 前端有封装函数，且被页面/hook 实际调用 |

**最大的空白**：**整个会话管理模块（5 个接口）一个都没接**；智能体只接了「注册」和「轮换 Key」，**没接查询/列表/更新/停用**；场景只接了「创建」；任务只接了「创建/更新/进度」，**没接列表/详情/完成**。

## 三、未使用接口按模块汇总（为什么没接）

| 模块 | 未接接口 | 现状/原因 |
| --- | --- | --- |
| 智能体 | 查询 / 列表 / 更新 / 停用 | 接入页只做「注册」，密钥页只做「轮换」；无智能体列表管理 UI |
| 记忆写入 | 异步写入 `async_write` | 后端占位能力，README 明确前端暂不启用 |
| **会话** | **全部 5 个** | **前端无会话管理模块**，会话仅作为记忆列表的过滤维度 |
| 场景 | 查询 / 列表 / 更新 / 停用 | 场景页只做「创建」，无场景管理 UI |
| 任务 | 查询 / 列表 / 完成 | 任务页只做「创建 + 进度」，无任务列表/详情/完成 |
| 检索 | 用户画像 `profile` | 前端用演示数据兜底，后端接口就绪后应切换 |
| 管理后台 | 全部记忆 / 记忆详情 | 无对应管理页面 |
| 生成 | 长对话压缩 / 上下文补全 | 无对应页面入口，对应设计文档 Section 5.4 的功能尚未做 |

## 四、使用正确性：5 处偏差/问题

1. **`/memory/list` 方法不一致（GET vs POST）**
   - 文档：`GET /api/v1/memory/list`。
   - 前端：`listMemories` 用 **POST**（[memory.ts:99](../src/api/modules/memory.ts#L99)），参数走 query string。
   - 备注：根目录 README.md 同样写成 `POST /memory/list`，且前端已联调通过——大概率是**文档（0813 版）滞后于实际后端**，建议与后端确认以哪个为准。

2. **`X-User-Id` 请求头未发送**
   - 文档 `search`/`context` 要求 `Header: X-API-Key, X-User-Id`。
   - 前端只发 `X-API-Key`（[client.ts:27](../src/api/client.ts#L27)），`user_id` 一律放在请求 body。若后端同时接受 body 中的 `user_id` 则无碍，否则需补齐该头。

3. **`deleteMemory` 存在 500 兜底（后端 bug 的 workaround）**
   - [memory.ts:153-181](../src/api/modules/memory.ts#L153)：`DELETE /memory/delete` 返回 5xx 时，自动改调 `PUT /memory/update {status:'deleted'}` 达到软删效果。
   - 代码注释明说「deployed single-delete endpoint currently returns 500」——这是**后端单删接口目前必 500** 的已知问题，前端做了补偿。后端修好后可移除该兜底。

4. **`listMemories` 做了双响应结构兼容**
   - [memory.ts:99-107](../src/api/modules/memory.ts#L99)：同时兼容「直接返回数组」和「`{items,total,page,page_size}`」两种响应，属防御性写法，与文档的 `{items,...}` 结构不冲突。

5. **认证头按配置选择性发送**
   - [client.ts:27-31](../src/api/client.ts#L27)：仅当 localStorage 配置了 `apiKey` 才发 `X-API-Key`。开发阶段后端 `AUTH_ENABLED=false` 无需认证，与文档「开发阶段无需认证」一致；生产启用鉴权后需确保配置项填写。

> 另：`MemoryContextPayload` / `MemorySearchPayload` 中 `include_preferences`、`include_facts`、`include_task_state` 等字段为前端自定义，文档未列出，属超集调用，一般无碍。

## 六、结论与建议

1. **核心闭环已通**：记忆写入、列表、更新、删除、统计、检索、上下文、生成（单/批/异步/状态）、监控类接口，前端均已真实对接并在页面使用。
2. **建议优先补齐**（对应后端就绪后）：
   - **会话管理 5 接口**（前端无会话模块，是最大的功能空白）；
   - **智能体列表/更新/停用**（当前只有注册和轮换 Key）；
   - **用户画像 `profile`**（替换分析页演示数据）；
   - **`delete-all` 接线**（封装已就绪，只差一个「清除全部」按钮）。
3. **建议与后端对齐确认**：
   - `/memory/list` 究竟是 GET 还是 POST（前端按 POST 联调通过）；
   - `search`/`context` 是否必须带 `X-User-Id` 头；
   - 单删接口 500 的修复进度（修复后前端可移除兜底逻辑）。
4. **建议清理**：删除死代码 `src/api/modules/dashboard.ts`（及重复类型）；`listAllMemories` 若短期内无需求可一并移除。
