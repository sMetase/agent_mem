## 〇、后端同事提问答复：数据清洗在前端做（结论先行）

> 问题："记忆数据导入那块，后端能接收的数据格式已在文档里，但 OpenWebUI 导出数据得清洗之后才能用。另一位同事说在 OpenWebUI 端不好办，问能不能在前端做？"

**结论：能做，且应当在前端做。** 无需离线处理。

**理由**
1. 前端导入页（`src/pages/Ingestion/`）已有「上传文件 → 解析 → 逐条调 `POST /memory/write`」完整链路，只是当前假设"输入已是清洗好的扁平记录"。要做的是在解析前加一层 **OpenWebUI 导出 → 后端契约** 的清洗适配器，复用现有链路。
2. 清洗是纯前端确定性文本转换，零 LLM / 零后端 / 零离线脚本依赖，浏览器内直接完成。
3. 交互闭环：导入页上传 OpenWebUI 原始导出 JSON → 前端自动清洗 → **清洗预览**（每条会话：消息数 / 摘要 / 时间 / 来源 / 校验状态）→ 确认后逐条 `POST /memory/write`（`interaction_type=session`，`session_id` 前端自动创建）。

**清洗规则（实现落点 `src/utils/openwebuiCleaner.ts`）**
- role 归一化：`user/assistant/system/tool` 保留；`function` 视为 tool；其余丢弃。映射到后端合法值 `user/assistant/system/tool/agent`。
- content 纯文本提取：字符串直接使用；数组（`[{type:"text",text:"..."}]`）拼接 text 片段；纯工具调用/空消息过滤。
- 会话元数据：`title` → `session_summary`、`created_at` → `session_time`（ISO 8601）、来源固定 `openwebui`。

**样例校准（已完成 2026-08-20）**：后端已提供真实 OpenWebUI 导出样例（`D:\PythonProject\openwebui_dataset\`，20 个主题目录，每个含多份 conversation-*.json）。**真实格式与通用假设不同**：
- 顶层是数组，每项一个会话，含 `title` / `models` / `history`；消息在 `history.messages`（**对象**，按 id 索引），不是数组。
- 顺序由 `parentId` / `childrenIds` 树表达，消息可能乱序，需按树序还原线性对话。
- 真实样例**无时间戳字段**（`created_at`/`session_time` 均无），`session_time` 留空；`session_summary` 取 `title`。

解析器已按真实格式校准：识别 `history.messages` / `messages`（对象或数组）、按 `parentId`/`childrenIds` 树 DFS 排序还原对话顺序、`title`→摘要、无时间戳留空。已用真实文件（conversation-000001.json，148 条消息）端到端验证：消息完整、顺序正确、来源 `openwebui`。

**待后端确认的清洗边界（不影响开工）**：tool 类消息（工具调用/返回）直接过滤不写入、`system` 保留 —— 是否 OK；前端清洗只保证格式符合契约，语义记忆抽取仍是后端 L1 的活。
