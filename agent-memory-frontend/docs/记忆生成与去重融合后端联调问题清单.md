# 记忆生成与去重融合后端联调问题清单

本文汇总“记忆生成与去重融合”前端全链路排查后确认的后端问题，供后端开发、算法和存储人员联合定位。前端已先完成模式切换、请求参数、异步任务恢复、结果归属、结果筛选和真实记忆 ID 展示的排查及修复；下述问题均通过直接 HTTP 请求复现，不依赖前端转换逻辑。

## 3. 结论摘要

| 编号 | 严重程度 | 结论 | 状态 |
| --- | --- | --- | --- |
| BE-GEN-01 | 高 | 完全相同文本在相同用户、场景和任务下重复提交，仍返回一个或多个 `keep_new`，未发生去重 | 稳定复现 |
| BE-GEN-02 | 高 | 显式请求 `preference` 且文本包含明确偏好时，返回成功但生成 0 条记忆 | 稳定复现，与用户手工现象一致 |

同步、批量、异步提交和状态轮询接口本身可访问；本次阻塞点是去重正确性、偏好抽取和写入后可查询一致性，而不是接口连通性。

## 4. 已确认问题

### BE-GEN-01：完全相同文本未去重

请求上下文保持完全一致：同一个 `user_id`、`scene_id`、`task_id`、`extraction_types` 和 `text`。

```json
{
  "user_id": "codex_backend_chain_20260717154551",
  "scene_id": "codex-chain-test",
  "task_id": "task_exact_duplicate",
  "extraction_types": ["key_fact"],
  "text": "隔离后端测试：项目 AURORA-R17 的唯一负责人是李雷，创建日期为2026年7月17日。"
}
```

第一次结果：

- `new_count = 1`
- `action = keep_new`
- `memory_id = mem_fe710e7059424882`
- 后端说明：`无相似向量匹配`

第二次提交完全相同请求：

- `new_count = 1`
- `merged_count = 0`
- `updated_count = 0`
- `discarded_count = 0`
- `action = keep_new`
- 返回新的 `memory_id = mem_4b52a377e5044ad8`
- 后端说明：`无匹配数据库记录`

使用另一个隔离用户再次复现时，第二次相同文本甚至返回 2 条新增记忆：

- `mem_0be427e117034de4`
- `mem_1250df4f562d4919`
- 两条均为 `keep_new`

预期行为：完全相同的有效记忆不应再次新增。后端应根据既定策略返回 `discard`、`merge` 或 `update_existing`，并保证相应计数字段与实际处理一致。

建议重点检查：

- 新记忆写入 Qdrant 后，下一次请求的相似向量召回是否使用相同 collection、用户和业务过滤条件。
- PostgreSQL 候选查询是否因 `scene_id`、`task_id`、状态或事务可见性条件漏掉刚写入数据。
- 向量写入失败或延迟时，是否有精确内容哈希、规范化文本或业务键兜底去重。
- 同一输入经 LLM 生成轻微不同表述时，去重阈值和关键词相似度是否仍能识别为同一事实。

### BE-GEN-02：偏好专用抽取返回空结果

请求：

```json
{
  "user_id": "codex_backend_chain_20260717154551",
  "scene_id": "codex-chain-test",
  "task_id": "task_preference_only",
  "extraction_types": ["preference"],
  "text": "隔离后端测试用户明确偏好：所有技术方案优先使用 TypeScript，并将回答控制在三点以内。"
}
```

实际响应为 HTTP 200、`code = 0`，但：

```json
{
  "memory_ids": [],
  "new_count": 0,
  "merged_count": 0,
  "updated_count": 0,
  "discarded_count": 0,
  "conflict_count": 0,
  "details": []
}
```

该文本包含明确、稳定、可复用的用户偏好，且请求只启用了 API 文档支持的 `preference` 类型。预期至少返回一条 `memory_type = preference` 的记忆，或在无法抽取时返回可诊断的原因，而不是成功空响应。

建议重点检查：

- `extraction_types` 到实际抽取器或 Prompt 分支的映射中，`preference` 是否已启用。
- 当前“3 路并行抽取”实现是否只执行关键事实、任务状态和历史决策，遗漏了偏好分支。
- 抽取结果被生成器、低价值过滤器或类型校验丢弃时，是否应写入 `details` 和 `discarded_count`。

### BE-GEN-03：生成响应与列表、检索可见数据不一致

API 文档将 `memory_ids` 定义为“本次实际存储的记忆 ID 列表”。聚焦一致性测试按顺序获得：

- 首次事实生成：1 个 ID
- 相同文本再次生成：2 个 ID
- 约束文本生成：1 个 ID
- 合计返回 4 个“已存储”ID

随后立即调用：

```text
POST /api/v1/memory/list?user_id=codex_backend_consistency_20260717154715&scene_id=codex-consistency-test&page=1&page_size=100
```

实际只返回第一次生成的 `mem_f3558b2e27884171`，`total = 1`。移除 `scene_id` 过滤仍为 1 条；等待 10 秒后再次查询仍为 1 条。

同一用户执行 `delete-all` 时，后端却返回：

```json
{
  "message": "成功删除 4 条记忆",
  "deleted_count": 4
}
```

另一组全链路测试也出现同类现象：生成阶段合计返回的 ID 数量大于列表可见数量；`search/context` 只能命中列表可见的第一条事实。

这说明至少有一个环节的契约不一致：

- `generate` 可能把未持久化、未激活或仅写入部分存储的候选计入 `memory_ids/new_count`；或
- `list/search/context` 可能使用了与生成、删除不同的状态、数据源或过滤条件；或
- PostgreSQL 与 Qdrant 双写存在部分成功，但接口仍按完整成功返回。

预期行为：同步生成返回成功时，`memory_ids` 中每个 ID 应在明确的一致性时限内被 `list` 查询到，并可参与 `search/context`。如双写部分失败，应回滚或返回失败/部分成功状态，不应继续以“实际存储”计数返回。

建议后端对同一个 ID 记录以下阶段日志：候选生成、去重决策、PostgreSQL 写入、事务提交、Qdrant upsert、状态字段、列表过滤、检索过滤，并在响应中提供可关联的 `trace_id`。

## 5. 需要后端确认的规则

发送 `extraction_types = ["key_fact"]` 且文本为“项目生产发布必须经过安全评审”时，后端稳定返回：

```json
{
  "action": "keep_new",
  "memory_type": "constraint",
  "content_preview": "项目 AURORA-R17 的生产发布必须经过安全评审。"
}
```

`constraint` 是 API 文档列出的合法响应记忆类型，因此前端已将其纳入“关键事实提取”页面的默认结果范围，不再隐藏该真实结果。请后端确认以下契约并补充文档：

- `extraction_types` 表示抽取器类别，而非最终 `memory_type` 白名单；
- `key_fact` 可以产生 `fact` 和 `constraint`；
- 如还可能产生其他最终类型，请给出完整映射表，便于前端筛选和测试。

| 健康检查 | HTTP 200，服务版本 1.0.0 |

“接口可用”仅表示传输和基本响应结构正常，不代表去重、偏好抽取和数据一致性已经通过验收。

## 7. 前端排查结论

前端已完成以下修复和验证，避免把前端状态问题误判为后端问题：

- 异步任务会持久化原始文本、来源页面预设、用户、场景、任务、会话及抽取类型，刷新后恢复到异步模式。
- 恢复任务明确显示“已恢复任务”和原始上下文，不再把旧异步结果显示为新单条同步请求的结果。
- 结果筛选使用提交任务时的预设，不受用户刷新后当前页面预设影响。
- “关键事实”结果默认包含后端合法返回的 `constraint` 类型。
- 单条同步、批量同步、单条异步均通过真实浏览器和在线后端验证，页面可展示统计、逐条动作及真实记忆 ID。
- 页面控制台未发现运行时错误；`pnpm check` 全部通过。

因此 BE-GEN-01、BE-GEN-02、BE-GEN-03 应从后端抽取、去重、持久化和查询一致性方向继续排查。

## 8. 后端修复验收标准

1. 相同用户、场景和任务下连续提交完全相同文本，第二次 `new_count = 0`，且返回可解释的去重动作。
2. 明确偏好文本在 `extraction_types = ["preference"]` 时至少生成一条可查询的 `preference` 记忆；若被过滤，响应必须体现过滤动作和原因。
3. 同步生成成功后，`memory_ids` 中每个 ID 均可由列表接口查询；检索和上下文接口使用一致的数据范围与状态规则。
4. PostgreSQL 或 Qdrant 任一写入失败时，不得以完整成功和新增计数返回；应回滚或显式返回部分失败。
5. 补充 `key_fact` 等抽取类型到最终 `memory_type` 的映射说明。
6. 为上述三项问题增加后端自动化回归测试，并提供可关联抽取、去重、双写和查询阶段的追踪标识。
