## 一、交接结论

当前后端基础健康接口、Dashboard 聚合接口、检索和上下文只读链路均已有可用响应；本轮前端已完成总览删减、真实数据接入和状态文案修复。后端仍需处理 Dashboard 响应契约不完整、智能体可选字段为空、上下文缺少 `latest_context`、历史告警缺少状态、统计口径不一致，以及公网管理接口鉴权和 HTTPS 等问题。以下标注“已改善”的历史问题仍需在后端交付和线上复验中闭环。

## 二、优先级说明

- **P0**：公网安全或核心链路不可用，发布阻断。
- **P1**：前端核心功能、数据口径或监控可信度受影响，需优先处理。
- **P2**：性能、契约完整性、运维可观测性或数据治理问题。

## 三、问题清单

### BE-001｜P1｜Dashboard 聚合接口已上线，但响应契约仍不完整

- **状态**：本轮直接请求 `GET /api/v1/admin/dashboard?hours=24&trend_days=7`，后端 `8000` 和前端代理 `8002` 均返回 HTTP 200、业务 `code=0`；上轮记录的 404 已改善。

- **仍缺/仍不稳定**：响应没有前端需要的 `latest_context`；除 `memory_trend` 外没有其他指标趋势序列；`comparison.retrieval_count_rate` 当前为 `null`；`recent_agents.scene_name/latest_result`、`recent_retrievals.memory_type/relevance_score` 存在 null；`recent_alerts` 没有当前/历史状态字段。
- **影响**：前端无法把上下文预览、趋势、列表空字段和告警状态表达为稳定的业务状态，只能使用明确空态或历史告警标签。
- **建议**：将下面 BE-017～BE-020 的字段补充到正式 response model、OpenAPI required/nullable 约束和示例中；保留 HTTP 200、业务 envelope、`generated_at`、时区和统计范围说明。

- **当前建议返回字段示例**：

  ```json

    "data": {
      "summary": {
        "agent_count": 0,
        "scene_count": 0,
  ```

- **验收**：无数据时返回空数组或 null，不用伪造值；百分比由后端计算；接口受管理员权限保护；字段和示例进入 OpenAPI；前端在缺字段时仍能显示可解释空态。

### BE-002｜P1｜`/admin/stats` 的统计维度不足（Dashboard 已承担聚合维度）

- **当前响应**：本轮实测返回 `total_memories=6010`、`total_users=1`、`total_agents=16`、`total_sessions=1`。
- **缺失维度**：场景总量、时间窗口内检索次数、上下文成功率、生成/去重/融合统计、记忆类型分布、趋势和最近事件；这些维度目前由 BE-001 Dashboard 提供。
- **影响**：单独调用 `/admin/stats` 仍不能完成总览；前端已使用 Dashboard 优先、stats 降级，不从当前页分页样本推算全局数据。
- **建议**：继续由 BE-001 的聚合接口统一提供全局口径；明确 `hours`、`trend_days`、时区、去重规则、失败是否计入分母和权限范围。

### BE-003｜P1｜检索接口已恢复，需持续保证业务失败可观测

- **当前状态**：本轮真实浏览器和只读请求验证，“用户偏好”等检索请求已能返回真实结果；当前 `GET /api/v1/admin/retrieval-logs?page=1&page_size=20` 返回 HTTP 200、`code=0`、95 条记录。上轮多个查询统一返回 `SEARCH_FAILED` 的现象本轮未复现。
- **历史复现**：不带 API Key 发送只读请求时曾出现：

  ```text
  POST /api/v1/memory/search
  {"query":"用户偏好","user_id":"user_001","top_k":10,"rerank":false}
  ```

  返回 HTTP 200，但业务体为：

  ```json
  {
    "code": -1,
    "message": "检索服务暂时不可用",
    "data": {"query": "用户偏好", "results": [], "total_candidates": 0, "elapsed_ms": 0},
    "error_code": "SEARCH_FAILED"
  }
  ```

- **复核状态**：历史失败记录仍可能出现在 Dashboard 的 `recent_alerts`，但当前检索日志和 API 日志已能看到成功请求；需继续确认依赖异常时的错误链路。
- **建议**：持续排查检索依赖链（Embedding、向量库、关键词检索、Reranker 或其配置）；失败时返回真实 trace_id 和依赖错误分类，不要把失败伪装成成功 HTTP 200；成功、空结果和失败都写入可查询的检索日志。
- **验收**：有效查询能返回真实结果或明确的空结果；依赖不可用时返回标准错误状态/错误码，并能在后台日志中定位；恢复后前端总览不出现当前故障误报。

### BE-004｜P1｜API 日志把应用失败记录成成功

- **现象**：历史日志中 `POST /api/v1/memory/search` 曾记录为 `response_code=200`、`error_code=null`，但同一请求体实际为 `code=-1`、`SEARCH_FAILED`；本轮最新 `/api/v1/admin/stats`、`dashboard`、`retrieval-logs` 调用均记录为 200 成功。
- **影响**：前端监控页会把这些调用判为成功，失败调用统计和告警失真；后台人员无法仅通过 API 日志发现检索故障。
- **建议**：日志中同时记录 HTTP 状态和业务 `code/error_code`；应用失败至少写入 `error_code=SEARCH_FAILED`、`trace_id`；监控查询支持按业务错误码过滤。建议统一约定：业务失败使用非 2xx，或日志/客户端严格按响应体判定失败，不能两套口径并存。

### BE-005｜P1｜检索日志已恢复，但字段不足以支撑 Dashboard 解释

- **现象**：本轮 `GET /api/v1/admin/retrieval-logs?hours=24&page=1&page_size=20` 返回 HTTP 200、`total=95`；但 Dashboard 的 `recent_retrievals` 中 `memory_type` 普遍为空，部分 `relevance_score` 为空，日志接口本身也未返回应用的实际检索信号和分数解释。
- **影响**：前端已将这些字段显示为“未返回”，不会误报接口故障；但管理员仍无法核对查询命中的记忆类型、评分和实际检索路径。
- **建议**：每次检索请求无论成功、空结果还是失败都写入完整审计字段，至少包括 `request_id/trace_id/user_id/agent_id/query摘要/top_k/result_count/applied_signals/elapsed_ms/status/error_code/created_at`；对敏感 query 做脱敏或权限隔离。

### BE-006｜P0｜公网管理接口当前无需凭据即可读取全局数据

- **现象**：不带 `X-API-Key` 或 `Authorization`，可以直接读取 `/api/v1/admin/stats`、`/api/v1/admin/memories`、`/api/v1/admin/api-logs` 和 `/api/v1/admin/retrieval-logs`；OpenAPI 中这两个 Header 参数均标记为 `required: false`。
- **影响**：公网访问者可读取全局记忆内容、用户/智能体数量和运行日志；这不是前端隐藏菜单能够解决的安全问题。
- **建议**：立即确认当前环境是否误用了开发模式；生产管理接口至少要求管理员认证和权限校验，普通 Agent Key 不能直接获得全局管理权限；未授权返回 401/403，并在 OpenAPI 声明 security scheme。上线前使用无凭据、普通 Agent、管理员凭据分别验收。

### BE-007｜P0｜全链路使用 HTTP，API Key 存在明文传输风险

- **现象**：前后端地址均为 `http://120.27.207.238`；前端客户端配置会把 API Key 放入 `X-API-Key` 请求头。
- **影响**：公网链路上的凭据和业务数据可能被窃听或篡改；即使前端改为更安全的存储，HTTP 仍会暴露请求凭据。
- **建议**：使用 HTTPS 反向代理，强制 HTTP→HTTPS，配置 HSTS、合理的 CORS 来源和安全响应头；API Key 轮换、最小权限、撤销和泄露处置需要形成运维流程。

### BE-008｜P1｜错误响应契约不统一（Dashboard 404 历史问题已改善）

- **现象**：上轮不存在的 Dashboard 路由返回 FastAPI 默认体 `{"detail":"Not Found"}`；本轮 Dashboard 已返回 `{code,message,data}`，但其他路由缺失、参数错误、业务失败仍需确认是否统一使用 `{code,message,data,error_code,trace_id}`。
- **影响**：Dashboard 将接口缺失显示成通用“接口不可用”，定位信息丢失；不同错误分支的状态码和字段不稳定。
- **建议**：统一 401/403/404/409/422/500 的 HTTP 状态、业务 `code`、`error_code`、`trace_id` 和 `detail` 结构；全局异常处理器覆盖路由不存在和未捕获异常；所有响应示例进入对接文档。

### BE-009｜P1｜OpenAPI 关键响应 schema 基本为空

- **现象**：`/openapi.json` 中 `/admin/stats`、API 日志、检索日志、Agent/Scene/Session/Task 列表、`memory/search`、`memory/context`、异步生成状态等关键 200 响应的 schema 为 `{}`。
- **影响**：前端只能手写类型，无法通过 OpenAPI 生成客户端或在 CI 中校验字段；字段缺失、null、分页和错误变更容易在运行时才暴露。
- **建议**：为分页、统计、检索结果、上下文结果、任务状态、Dashboard 和错误体补充 Pydantic response model、required/nullable 约束、枚举、示例和错误响应；将 OpenAPI 作为前后端唯一契约源。

### BE-010｜P1｜单条记忆 DELETE 线上 500，前端被迫隐式降级

- **证据**：仓库 `src/api/modules/memory.ts` 已明确记录“deployed single-delete endpoint currently returns 500”，前端捕获 5xx 后改用 `PUT /api/v1/memory/update` 将状态置为 deleted。本次没有主动执行 DELETE，以避免修改线上数据；既有联调文档也记录过该问题。
- **影响**：DELETE 语义与实际软删除行为不一致；前端无法判断删除是否真的完成，且隐藏降级会掩盖服务端错误。
- **建议**：修复 `DELETE /api/v1/memory/delete`，明确软删除、向量索引清理、幂等性和返回体；修复后用测试数据复验成功、重复删除、不存在 ID、权限不足和索引清理。若最终只保留 PUT，请正式废弃 DELETE 并更新 OpenAPI/前端。

### BE-011｜P1｜检索请求缺少模式和可解释性字段

- **现象**：OpenAPI 的 `MemorySearchRequest` 只有 query、范围、类型、Top-K、时间、include_scores、rerank 等字段，没有 `retrieval_mode`；响应 schema 也没有 `applied_signals`、`score_breakdown` 等实际策略说明。
- **影响**：前端的语义/关键词/元数据/融合子入口无法验证后端实际执行路径，后台也无法解释结果来源。
- **建议**：增加可选 `retrieval_mode`（或明确单一混合检索契约），响应返回实际应用信号、各信号分数/权重、候选数、最终排序和耗时；失败和降级时返回使用了哪条路径。

### BE-012｜P2｜健康接口口径分裂，无法反映依赖可用性

- **现象**：`8000/health` 返回应用名、版本和 status；`8000/api/v1/health` 返回 `status=ok,database=true`；但 `8002/health` 返回前端 HTML。仓库前端本轮已改为请求 `/api/v1/health`，不再依赖前端端口的根路径。
- **影响**：根路径健康检查仍容易受反向代理配置影响；即使 API 健康接口返回正常，当前响应也没有向量存储、Embedding/Reranker 等依赖状态。
- **建议**：保持 `/api/v1/health` 为稳定 JSON，并在 OpenAPI 中声明；区分 liveness/readiness；提供统一依赖检查和降级状态，至少包含数据库、向量存储、Embedding/Reranker 配置和版本；定义超时、缓存和敏感错误信息规则。若继续支持 `/health`，请将 `8002/health` 正确代理到后端，不能返回前端 HTML。

### BE-013｜P2｜上下文接口存在明显耗时风险，需要建立 SLO

- **现象**：只读调用 `POST /api/v1/memory/context` 成功，但一次请求响应头记录 `x-response-time: 3166.66` ms，返回内容较大。
- **影响**：上下文页面和外部 Agent 可能等待数秒以上；若并发上升，容易放大模型/检索依赖压力。
- **建议**：按查询长度、Top-K、是否重排分组统计 p50/p95/p99；建立超时和降级策略，限制返回体/Token，优化重复查询缓存和依赖并发；在日志中记录各阶段耗时。

### BE-014｜P1｜线上数据与联调测试数据混用

- **现象**：公网管理列表中可见 `测试场景`、自动回归场景、`测试A`、`Fmt`、`other` 等测试性质的智能体/场景；全局记忆列表也混有测试用户和测试任务数据。
- **影响**：Dashboard 总量、趋势、检索结果和监控统计被测试数据污染；真实用户或评审者可能看到不应出现的内容。
- **建议**：生产、测试、演示环境使用独立数据库/租户/命名空间；清理或隔离测试数据前先备份并由负责人确认，不要直接在生产执行批量删除；Dashboard 明确统计范围和租户边界。

### BE-015｜P2｜历史 422 请求需要追溯来源

- **现象**：过去 24 小时 API 日志中存在 `/api/v1/memory/stats` 的 422 记录；当前带 `user_id=user_001` 的请求可正常返回 200，缺少 user_id 时后端会返回标准 422。
- **影响**：说明曾有调用方漏传必填参数或配置为空；目前尚不能仅凭日志判断是旧版前端、手工请求还是其他客户端。
- **建议**：日志补充请求来源/版本/Agent/trace_id 和校验详情；前端在发请求前阻止空 User ID；后端保留结构化 422 详情并提供按 trace_id 的查询能力。

### BE-016｜P2｜异步接口的生产状态和契约需要统一

- **现象**：OpenAPI 已列出 `POST /api/v1/memory/async_write`、`POST /api/v1/memory/generate/async` 和状态查询，但关键响应 schema 为空；项目既有文档对 async_write 的“占位/降级同步”和 async generate 的实现状态描述不完全一致。
- **影响**：前端无法可靠判断是否可以启用异步导入、任务是否持久化、重启后是否可恢复以及失败重试语义。
- **建议**：明确每个异步接口的 202/200 状态、request_id、状态枚举、进度单位、结果保存时长、重启恢复、取消和幂等键；补齐 OpenAPI 和 staging 验收，前端据此接入 FE-011。

### BE-017｜P2｜Dashboard 指标趋势和日环比字段不完整（当前总览暂不展示）

- **现象**：当前 Dashboard 只返回 `memory_trend`；接入智能体、业务场景、近 24 小时检索调用和上下文成功率没有对应趋势序列。`comparison.retrieval_count_rate` 当前为 `null`，其他日环比字段虽有值，也没有明确统计时区和分母口径。
- **前端处理**：本轮总览五张指标卡已收敛为只展示标题和当前实际值，趋势与日环比从卡片移除；独立记忆趋势区仍消费 `memory_trend`，没有趋势时显示明确空态，不会显示“接口不可用”。
- **需要后端交付**：当前趋势和日环比不再是总览卡片的发布阻塞项。若后续产品恢复这些展示，后端需提供带日期、时区、统计范围和分母口径的稳定字段；若需要前端说明数据新鲜度，还需提供 `generated_at`/`as_of`，并在 OpenAPI 中声明缺失趋势是正常状态。
- **验收**：无数据返回空数组/`null`；有数据返回带日期、时区和统计范围的序列；`retrieval_count_rate` 说明为何为空或补齐。

### BE-018｜P1｜recent_agents 的场景和最近结果字段为空

- **现象**：当前 `recent_agents` 正常返回 5 条记录和 `agent_id/status/last_write_at`，但部分记录 `scene_name`、`scene_id` 同时为空，5 条记录的 `latest_result` 均为空。
- **前端处理**：前端列表已固定列宽、支持横向滚动和长 ID 省略；字段为空时显示“未返回”，不再把字段缺失显示成“接口不可用”。
- **需要后端交付**：确认 `scene_name`、`scene_id`、`latest_result` 是否为必需字段。若场景可由 Agent 关联关系推导，请在聚合接口中返回最终展示值；若没有最近写入结果，请明确返回 `null` 的业务含义，并在 OpenAPI 标记 nullable。
- **验收**：列表 5 列均有稳定 schema；可选字段为空时有统一语义；长 Agent ID 不影响其他字段读取。

### BE-019｜P1｜Dashboard 缺少 latest_context，且历史告警没有当前状态

- **现象**：Dashboard 响应当前没有 `latest_context`，导致总览无法展示最近一次真实上下文。`recent_alerts` 返回了 5 条历史 `/api/v1/admin/retrieval-logs` HTTP 500 记录，但没有 `status` 或 `resolved_at`，前端无法仅靠响应判断告警是否仍然有效。
- **前端处理**：上下文缺字段已改为空态提示；告警按“当前告警/已恢复/历史告警”显示，缺少状态字段的记录默认标记为历史告警；当前状态另由最近 1 小时 API 日志计算。
