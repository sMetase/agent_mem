# 前端问题文档

> 检查时间：2026-07-21～2026-07-22（北京时间）  
> 检查对象：线上前端 `http://120.27.207.238:8002/`、仓库 `E:\memory_frontend` 以及当前后端接口行为。  
> 检查原则：本次使用真实浏览器执行总览及监控页面冒烟测试，并辅以只读 GET 请求和不会修改数据的检索/上下文请求；未执行注册、写入、生成、更新、删除等变更操作。

## 一、结论摘要

系统的所有主要路由都可以打开，浏览器没有发现 Console error/warn 或 React 错误覆盖层；仓库的 `pnpm lint`、32 个单元测试和 `pnpm exec tsc --noEmit` 也全部通过。

但线上仍有几类前端问题：

1. 上轮发现的 Dashboard 聚合接口问题已有改善：本轮 `/api/v1/admin/stats` 和 `/api/v1/admin/dashboard?hours=24&trend_days=7` 均返回 HTTP 200、`code=0`，但前端仍把缺趋势数据、空字段、历史失败告警和缺失响应字段统一显示为“接口不可用”。
2. 用户级、会话级、任务级记忆页面没有把范围条件传给后端，当前看到的是分页样本或本地过滤结果，页面标题和统计口径不可信。
3. 检索、上下文、智能体、场景、任务等页面存在“页面入口已提供，但实际模式/列表/管理能力未接上”的情况。
4. 总览中的智能体列表虽然已返回 5 行和 5 列数据，但长 Agent ID 撑大首列，桌面端和移动端均把其余列推出可视区域；同时后端部分可选字段为空，导致列表内容进一步退化。
5. 公共壳层仍有多个演示型或无动作控件，凭据保存策略和错误反馈也不适合生产联调。

## 二、优先级说明

- **P0**：发布/安全阻断，或可能把错误数据暴露给用户。
- **P1**：核心功能不可用、数据口径错误，需优先修复。
- **P2**：明显的功能缺口、性能或可用性问题。
- **P3**：体验优化或产品口径待确认项。

## 三、问题清单

### FE-001｜P1｜Dashboard 已恢复取数，但仍把多种非接口故障显示为“接口不可用”

- **复核结论**：上轮记录的 Dashboard 聚合接口 404 已不再复现。本轮直接请求 `GET /api/v1/admin/stats` 和 `GET /api/v1/admin/dashboard?hours=24&trend_days=7`，在后端端口 `8000` 及前端代理端口 `8002` 均返回 HTTP 200、`code=0`。页面实际取得了接入智能体 16、业务场景 4、记忆总量 6,010、今日检索调用 95 等数据。
- **真实原因**：当前页面中的“接口不可用”至少来自以下不同情况，不能继续按统一接口失败处理：
  - **指标卡趋势占位误用错误文案**：后端只返回 `memory_trend`，其余指标没有对应趋势数组；指标主值和统计接口均成功，但趋势区域复用了“接口不可用”兜底文案，应显示“暂无趋势数据”或“实时数据”。
  - **智能体列表的可选字段为空**：`recent_agents` 正常返回 5 条记录，但部分记录的 `scene_name/scene_id` 为空，5 条记录的 `latest_result` 均为空；前端把空字段映射成“接口不可用”。
  - **检索列表的元数据为空**：`recent_retrievals` 正常返回记录，但抽样记录的 `memory_type` 为空，部分记录的 `relevance_score` 为空；这表示字段缺失，不表示检索日志接口失败。
  - **上下文预览契约缺字段**：Dashboard 响应不包含前端读取的 `latest_context`，因此上下文预览必然走“接口不可用”兜底；这是响应契约不一致或功能未提供，不是网络不可达。
  - **历史告警被当作当前故障**：Dashboard 返回的 `recent_alerts` 中有 5 条 2026-07-21 16:06～16:19（北京时间）的 `/api/v1/admin/retrieval-logs` HTTP 500 历史记录；本轮当前请求该接口已返回 HTTP 200、`code=0`，监控页也显示 95 条记录。页面没有区分历史告警和当前状态，造成“现在仍不可用”的误导。
  - **统计口径不一致**：`summary.memory_count=6010`，而 `memory_trend` 最新点的 `total=6047`，相差 37；这不是前端渲染错误，但前端不应在未标明口径的情况下并列展示。
- **影响**：用户无法区分接口失败、字段为空、暂未提供趋势、历史告警和数据口径不一致；总览可取到真实数据却仍呈现大面积故障感知。
- **建议**：前端将“请求失败”“字段为空”“暂无趋势数据”“历史告警”拆成不同状态；空字段使用 `-` 或“未返回”，并保留字段提示；上下文预览与后端确认 `latest_context` 契约后再展示；告警显示发生时间、当前/历史状态和 trace ID；趋势和统计明确数据口径。后端需要配合补齐字段和口径，详见后端交接文档对应事项。
- **本轮处理状态**：仓库已改为真实读取 `stats/dashboard`；五张指标卡已移除趋势和日环比展示，只保留标题与实际数据。独立记忆增长趋势缺失时显示“暂无趋势数据”，不再显示“接口不可用”；后端趋势序列不再是当前总览卡片的阻塞项。

### FE-002｜P2｜Dashboard 数据新鲜度与刷新机制需明确

- **现象**：总览页面不再提供手动刷新按钮，也不再显示“总览数据来自”等同行说明；五张指标卡只展示指标标题和当前实际值。当前页面没有展示 `generated_at` 或明确刷新周期，数据更新依赖页面重新加载。
- **影响**：用户会误以为数据持续更新，无法判断数据是否过期。
- **建议**：如果产品仍要求判断数据新鲜度，后端应提供 `generated_at`/`as_of`、统计时间范围和时区；前端再按确认后的口径显示“最近同步时间”或刷新周期，不使用“实时”暗示持续推送。
- **本轮处理状态**：按本轮需求已移除手动刷新按钮和同行说明，指标卡已收敛为“标题 + 实际数据”；自动刷新和同步时间属于待产品/后端确认事项。

### FE-003｜P1｜仓库源码、线上构建和原型路由不一致

- **现象**：仓库 `src/pages/ModernPrototype/index.tsx` 仍包含固定的 `128`、`24`、`2,486,920`、`83,214`、`99.2%`、静态表格和静态趋势；本轮已将 `src/pages/Overview/index.tsx` 改为真实 Dashboard 数据实现，但线上 `/` 尚未重新部署，隐藏路由 `/prototype` 仍可直接访问并展示演示数据。
- **影响**：线上问题无法由当前仓库稳定复现；重新部署时可能再次发布演示数据；用户可通过直接 URL 看到与真实系统冲突的指标。
- **建议**：确定唯一生产首页实现；删除或仅在开发环境注册 `/prototype`，或者增加明显的“原型预览”标识和权限；发布前校验产物 commit、构建时间和资源 hash，避免线上构建来源不明。

### FE-004｜P1｜记忆分层页面没有按实际层级/范围查询

- **现象**：`src/pages/Memory/index.tsx` 的 `listMemories` 调用只传 `userId`，没有传 `memory_scope` 或 `session_id`；会话页初次加载 100 条用户记忆，再在浏览器内筛选；任务页只有输入 Task ID 后才把 `task_id` 传给接口。用户级页面也没有传 `memory_scope=user`。
- **线上证据**：后端 `memory_scope=user` 返回 0 条、`memory_scope=session` 返回 240 条；但线上 `/memory/session` 页面显示 100 条，并能看到不同类型、任务 ID 的混合记录。
- **影响**：页面标题、总数、分页和“范围内记忆”均可能与真实数据不符；超过当前加载批次的匹配数据会漏掉。
- **建议**：为列表请求补充 `memoryScope`、`sessionId`、`taskId` 参数，并由后端分页；范围页使用服务端 `total`，没有匹配时显示空态，不要用当前数组长度冒充总量。

### FE-005｜P1｜检索子入口的模式只改变文案，没有形成真实请求模式

- **现象**：语义、关键词、元数据、融合、Top-K 五个路由都调用同一个 `POST /api/v1/memory/search`；前端没有发送 `retrieval_mode`，主要差异只有是否发送 `rerank`。页面却分别宣称“向量相似度”“关键词匹配”“字段过滤”“多路召回”等不同策略。
- **影响**：验收人员无法从请求或响应判断页面实际采用了哪种策略；用户可能把同一套结果误认为不同算法结果。
- **建议**：若后端支持多模式，前端发送明确的模式字段并展示实际应用信号；若后端暂不支持，统一文案为“由后端执行混合检索”，不要承诺未验证的算法。后端契约见 BE-012。

### FE-006｜P2｜上下文子入口没有完整表达模式和会话范围

- **现象**：JSON、文本、相关性、长度控制等路由都复用同一个 `POST /api/v1/memory/context`，主要是前端切换标题、规则和展示方式；表单没有 `Session ID`，请求也没有发送 `session_id`，只能传当前配置的 Scene ID 和可选 Task ID。
- **影响**：会话上下文无法从页面直接限定；“JSON 返回”“文本返回”“长度控制”等入口不能验证后端是否真正按模式处理。
- **建议**：补充 Session ID/Scene ID 的明确输入或选择；与后端约定 `output_mode`、压缩策略和返回字段，页面展示后端实际响应，而不是仅改变前端视图。

### FE-007｜P1｜智能体接入页面缺少已有智能体的浏览和选择

- **现象**：线上 `/access/agents` 只提供“注册新智能体”，当前身份只展示本地保存的 Agent ID；仓库 `src/api/modules/agent.ts` 也只有注册和轮换密钥方法。
- **线上证据**：后端 `GET /api/v1/agent?page=1&page_size=5&is_active=true` 可返回已存在的智能体列表，实测有 14 个 active agent。
- **影响**：无法从系统中选择已有身份、查看状态、切换当前 Agent 或停用旧身份；重复进入页面容易重复注册。
- **建议**：增加列表、筛选、详情、启用/停用和“设为当前身份”能力；注册后刷新列表而不是只写入浏览器配置。

### FE-008｜P1｜场景管理页面缺少已有场景的浏览和选择

- **现象**：线上 `/access/scenes` 只提供创建场景和展示当前本地 Scene ID；仓库 `src/api/modules/scene.ts` 只有 `createScene`。
- **线上证据**：后端 `GET /api/v1/scene?page=1&page_size=5&is_active=true` 可返回 4 个 active scene。
- **影响**：无法选择、修改、停用已有场景；智能体注册表单要求手填 Scene ID，容易产生不存在或拼写错误的隔离范围。
- **建议**：增加场景列表/选择器、详情、编辑、停用和创建后自动刷新；注册智能体时使用场景选择器而不是纯文本输入。

### FE-009｜P1｜凭据管理把完整 API Key 持久化在 localStorage

- **现象**：`src/utils/storage.ts` 将 `apiKey` 与其他配置一起写入 localStorage；接口客户端每次请求从该存储读取并发送 `X-API-Key`。
- **影响**：同一浏览器内任何可执行脚本都可能读取长期凭据；当前服务使用 HTTP 时还存在明文传输风险。后端鉴权和 HTTPS 事项见 BE-005、BE-006。
- **建议**：明确凭据生命周期；优先使用服务端登录/短期令牌或至少使用 session 级存储、最小权限和显式清除；页面不得在列表/截图中暴露完整 Key，并提供连接校验和失效提示。

### FE-010｜P2｜任务页面只能手动输入 Task ID，未接入任务列表和完成动作

- **现象**：`src/pages/Task/index.tsx` 只有创建任务、更新进度和查询进度；`src/api/modules/task.ts` 没有任务列表、详情和完成接口。
- **线上证据**：后端已经提供 `GET /api/v1/task`、`GET /api/v1/task/{task_id}` 和 `POST /api/v1/task/{task_id}/complete`。
- **影响**：用户无法浏览当前用户已有任务、恢复任务或通过页面完成任务；任务 ID 只能靠复制粘贴。
- **建议**：增加任务列表、状态筛选、详情、继续执行和完成按钮；创建后回到列表并支持直接打开任务。

### FE-011｜P2｜导入按记录串行写入，缺少批量/异步/恢复能力

- **现象**：`src/pages/Ingestion/index.tsx` 在 `for ... await` 循环中逐条调用 `POST /api/v1/memory/write`；中途失败后只能显示“部分完成”，没有断点、重试、取消或失败记录下载。
- **影响**：大文件导入耗时随记录数线性增长，网络抖动会造成部分写入且难以恢复；后端已有批量/异步能力但前端没有利用。
- **建议**：小批次使用 batch 接口，长任务使用 async 接口并显示 request ID/进度；保留失败行、重试和取消能力，并在完成后重新拉取服务端结果。

### FE-012｜P2｜错误反馈丢失错误码、Trace ID 和可操作的重试入口

- **现象**：`unwrapApiResponse` 能接收 `error_code/trace_id`，但 `getErrorMessage` 只取 message；检索失败页面只弹出“检索服务暂时不可用”，Dashboard 失败区也只显示“接口不可用”。
- **影响**：前端无法帮助用户区分参数错误、权限错误、接口缺失和服务异常，后端人员也拿不到前端页面上的定位信息。
- **建议**：统一错误组件显示用户可读提示、error code、Trace ID 和重试按钮；对 401/403/404/422/5xx 分别处理；Dashboard 的缺失接口使用空态而不是错误态。

### FE-013｜P2｜公共壳层存在固定数据和无动作控件

- **现象**：`src/layouts/AppLayout.tsx` 中全局搜索框没有搜索处理，通知角标固定为 12，折叠菜单按钮没有 onClick，帮助按钮和管理员下拉菜单没有实际动作；用户身份固定显示 `admin/系统管理员`。
- **影响**：控件看起来可用但点击无结果，容易在演示和验收时造成误判；固定管理员身份与当前仅本地 User ID 的实际身份模型不一致。
- **建议**：未实现的控件暂时隐藏或标注“规划中”；实现搜索、通知、帮助、侧栏折叠和退出逻辑后再展示；用户身份从真实登录/权限上下文读取。

### FE-014｜P1｜健康检查请求打到前端端口，页面将 HTML 当成非健康响应

- **现象**：线上前端默认 `baseUrl` 是 `http://120.27.207.238:8002`，`getHealth()` 调用的是根路径 `/health`。真实浏览器打开 `/monitoring/health` 后显示“状态未知”“应用：未知，版本：未知，状态：未知”和“后端返回非健康状态”。浏览器没有 Console error，是因为 `8002/health` 实际返回了 HTTP 200 的前端 HTML，而不是健康检查 JSON。
- **证据**：只读请求对比：`8000/health` 返回 `{"status":"ok","app":"Agent Memory System","version":"1.0.0"}`；`8002/health` 返回 `text/html` 的前端首页；`8000/api/v1/health` 和 `8002/api/v1/health` 返回 JSON `{"status":"ok","database":true}`。这说明普通 `/api/v1/...` 请求可以经 `8002` 代理，但根路径 `/health` 没有正确代理到后端。
- **影响**：健康检查页无法真实反映后端服务状态；用户会把“端口/反向代理配置错误”误认为后端服务不健康。即使修正路径，当前页面仍只展示进程和数据库级信息，未覆盖向量库、模型等依赖。
- **建议**：统一前端 API base URL 和健康检查契约，优先调用可验证 JSON 的 `/api/v1/health` 或把 `/health` 正确代理到后端；前端校验响应 `Content-Type` 和必需字段，HTML 不得被当作健康响应；再分别展示 API、数据库、向量库、Embedding/Reranker 等依赖，并明确 liveness 与 readiness 的区别。
- **本轮处理状态**：仓库 `getHealth()` 已改为调用 `/api/v1/health`；本地浏览器验证显示“后端健康检查通过”。线上页面需随本次构建重新部署后复核。

### FE-015｜P2｜移动端 Dashboard 表格缺少可控的横向滚动/卡片降级

- **现象**：在 390×844 视口下，Dashboard 的多列 Agent/检索表格不能稳定展示；表格内容宽度远大于容器，页面整体出现横向溢出或列内容被挤压。
- **影响**：手机或窄屏评审时无法稳定查看关键字段和状态，也无法判断是数据缺失还是布局裁切。
- **建议**：为表格容器增加受控横向滚动，或提供移动端卡片视图；固定关键列宽、长文本省略并提供详情/复制入口，避免整页横向溢出。
- **本轮处理状态**：智能体表格已设置固定列宽、`table-layout="fixed"` 和 `overflow-x: auto`；本地 390×844 浏览器验证容器宽 298px、表格宽 890px，可横向滚动，未发生整页横向布局破坏。

### FE-016｜P2｜缺少线上路由和接口契约的自动化回归

- **现象**：仓库现有 9 个 Vitest 测试文件、37 个单元测试，没有 Playwright/Cypress 等浏览器 E2E，也没有针对线上关键路由、Dashboard 聚合字段/空态、检索失败和权限态的自动化契约测试。
- **影响**：本次发现的“页面能打开但接口口径错误/模式未接线”类问题不会被现有测试拦截。
- **建议**：加入最小 E2E 矩阵：首页、记忆分层、检索成功/失败、上下文成功、监控 401/403、空数据和移动端布局；发布前运行 against staging。

### FE-017｜P1｜总览“智能体接入与数据写入”列表被长 Agent ID 撑坏，实际只看得到第一列

- **现象**：真实浏览器在桌面端 1280×720 和移动端 390×844 均复现：DOM 中实际存在 `Agent ID`、`场景`、`接入状态`、`最近写入`、`结果` 5 个表头和 5 行记录，但页面视觉上基本只显示 Agent ID，其他列被推出可视区域。最长的一条 `mem_c4485c5d9e18d7a8dea02231a4adcf9014601b0c65d746a118a901908d54379b` 使首列扩展到约 576px；表格总宽约 877px，桌面容器约 360px、移动容器约 329px，容器 `overflow-x` 为 `visible`，没有省略、固定布局或可用的横向滚动。
- **数据层补充**：该表并非列表接口不可用。Dashboard 已正常返回 5 条 `recent_agents`；但第 1、4、5 条没有场景名称/场景 ID，第 3 条没有场景名称只能回退到 `scene_id`，5 条记录的 `latest_result` 均为空。前端将这些空值也显示为“接口不可用”，进一步加重了“列表只有 ID”的问题。
- **影响**：总览无法同时核对 Agent、场景、接入状态、最近写入和写入结果；长 ID 还会改变列宽，导致桌面端和移动端的验收结果均不稳定。
- **建议**：Agent ID 列使用固定宽度、`ellipsis`、Tooltip 和复制按钮；表格设置 `table-layout: fixed`，容器使用受控 `overflow-x: auto`，移动端降级为卡片或详情抽屉；空字段统一显示 `-`/“未返回”，不要使用“接口不可用”；后端补充 `scene_name`、`latest_result` 的字段保证或明确其为空的业务含义。
- **本轮处理状态**：仓库已完成上述前端修复，Agent ID 支持省略、Tooltip/复制，表格保留完整 5 列；空字段显示“未返回”。本地桌面和 390×844 移动端均已验证，线上需重新部署后复核。
